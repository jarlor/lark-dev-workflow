# 飞书研发工作流

一份可复制的飞书研发管理模板，以及操作它的 `lark-dev-workflow` Skill。默认一个 Base 管理多个项目，每次操作使用“06 项目”中的真实项目 ID。

**[使用飞书模板](https://qa2vxy8qipi.feishu.cn/base/O2Tjbsrt7a1XorsQ9O1cKbtJnWg?table=tblmruIMSZp7rVPw&view=vewOKMstkv)** · **[安装 Skill](#安装)** · **[下载 v1.4.1 完整发布包](https://github.com/jarlor/lark-dev-workflow/releases/tag/v1.4.1)**

在线模板名称为 **Agent研发工作流｜v1.2.0**，对应模板规范 `1.2.0`。当前 Skill 与完整包为 **v1.4.1**。 打开模板后点击「使用该模板」，在自己的飞书空间生成副本，再把副本链接交给 Agent 接入。

| 交付物 | 位置 | 用途 |
|---|---|---|
| 通用 Skill | `skill/lark-dev-workflow/` | 理解反馈、确认修订、判断证据与流转、核对范围并回写 |
| 飞书模板 | `template/` | 项目与业务表、反馈表单、状态选项、原生关联、日常视图和文档容器 |
| 项目配置 | 目标项目的 `.lark-dev-workflow/project.json` | 绑定共享 Base 中本项目的真实记录、字段、文档章节和维护约定 |

模板提供结构和入口，Skill 负责业务判断。具体边界见 [模板与 Skill 职责](模板与Skill职责.md)。

## v1.4.1 按时间分批处理

每轮会把实际运行时限和本轮截止参考时间交给 Codex，并要求提前留时间核对已写内容、保存结果。事项较多时先完成一部分，再在下一轮继续；超时后的恢复仍先核对实际结果，避免重复操作。运行配置、旧会话进度和模板结构继续兼容，无需改表。

## v1.4.0 本人网页接入

可选择两种本人访问方式：

- **已有 CLI 用户 profile**：继续使用原 Lark CLI 登录和相应 `lark-*` 工具。
- **不创建应用或 bot**：复用本人已经登录的飞书网页，不填写虚构 profile，也不借用其他项目的应用。需要 Node.js 22+ 和现有浏览器的本机连接；只操作自己的临时标签，不导出登录凭据。详见 [本人网页接入](skill/lark-dev-workflow/references/browser-access.md)。

首版网页读取只支持已有格式 2、`project_record`、Base-only 的项目绑定，非空 Docx 绑定暂不支持。缺“反馈项目”时可明确选择 `linked_only`，只读取已关联事项；未归属的新反馈不在覆盖范围内。保留原绑定和模板，不自动加字段。

`scan` 只读记录和评论，不写飞书、不启动 Codex 工作、不安装 cron。已在目标 Linux 完成真实本人网页只读扫描：两轮表格和评论一致、项目过滤通过。评论范围限当前账号网页可见的索引及已加载内容；真实长线程和已解决样本尚未实测。网页写入、回复和定时运行还需分别验证；本次未启用 cron。

## v1.3.2 更新

旧反馈表没有“反馈项目”时，可在候选绑定中明确选择 `feedback_intake.mode=linked_only`，只扫描已关联本项目的事项与可核实归属的评论。运行结果会说明未归属的新反馈未被扫描；默认分流模式和项目隔离检查保留，不自动加字段或改绑定。该版运行器使用 CLI，需在目标机器完成本人登录。详见 [旧表适配](skill/lark-dev-workflow/references/project-mapping.md#没有反馈项目的旧反馈表)。

## v1.3.1 更新

修复只用 Base、没有 Docx 的已有项目无法进入评论采集和 Linux 运行器的问题；每轮明确载入项目规则，保留禁止评论等项目约定。已配置的文档仍严格验证，字段映射和本人 CLI 接入仍需真实核实。模板结构、历史标签与原项目数据不变。

## v1.3.0 功能

该版增加 Linux 定时入口，并明确反馈拆分后的确认流程；已有模板副本无需迁移。

- **表格内容更好懂**：标题、结果、下一步和缺少的信息直接写具体事情，减少官方式表述；保留原始反馈和必要条件。
- **通过表格沟通**：处理项目时，默认允许 AI 用已登录用户的身份评论、提问和回复。只读、停止和项目范围要求继续有效。
- **先确认再开发**：不清楚的反馈在原记录评论中 @ 反馈人澄清；拆分出需求或 Bug 后立即评论，用简单的话说明准备做什么，请相关反馈人明确确认，再安排开发。Bug 同时需要复现依据。详见 [澄清与确认](skill/lark-dev-workflow/references/feedback-confirmation.md)。
- **Linux 定时运行**：随 Skill 提供 `.sh` 入口，由系统 crontab 每隔几分钟检查记录和评论，有变化或有待继续工作时启动 Codex CLI。需要人回答时在事项下留言，不要求人在终端守着。

Linux 的配置、试跑、安装、暂停及移除方法见 [定时运行说明](skill/lark-dev-workflow/references/unattended.md)。这套工具不依赖 Codex App，也不修改飞书模板字段；真实机器的登录、读取、回写和 cron 运行还需部署时验证。

## 安装

安装当前版本：

安装到 Codex 的全局 Skill 目录：

```bash
npx skills add jarlor/lark-dev-workflow --skill lark-dev-workflow --agent codex -g
```

去掉 `-g` 可安装到当前项目；其他 Agent 按安装器提示选择。当前安装器会把 Codex 全局 Skill 放在 `~/.agents/skills/lark-dev-workflow`，以实际安装输出为准；已有手动安装也可以保留自己的位置。[安装器说明](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)

固定使用本版本时，可从标签路径安装：

```bash
npx skills add https://github.com/jarlor/lark-dev-workflow/tree/v1.4.1/skill/lark-dev-workflow --agent codex -g
```

Linux 已安装时，可重新执行上面的固定版本安装命令更新本 Skill。先保留项目配置和运行状态；手动安装或本地改过 Skill 的机器，先核对安装位置与差异，不覆盖个人修改。不要为了更新本技能运行会更新所有技能的命令。

更新完成后，在新启动的 Codex CLI 会话中读取新版 Skill；已有会话主动重新读取 `SKILL.md` 及本次相关说明，不能假定上下文自动更新。更新本身不登录飞书、不启动业务处理、不安装 cron；首次启用 Linux 定时运行按 [配置与试跑](skill/lark-dev-workflow/references/unattended.md#配置并试跑) 执行。已有运行器先暂停后续周期并等当前轮次结束，再更新文件；配置、进度和既有项目契约均保留。

运行前准备：

- `skills` 安装器需要 Node.js；当前官方要求 Node.js 22.20 或更高。
- 辅助脚本需要 Python 3.9 或更高，仅使用标准库；可选的定时入口另需 Linux、Codex CLI 和系统 crontab。
- 网页途径需要 Node.js 22+，复用本机已有、本人已登录的浏览器；配置步骤见 [网页接入说明](skill/lark-dev-workflow/references/browser-access.md)。不要求安装 Lark CLI，不因缺 profile 创建应用或 bot。
- 已有可用 CLI 用户 profile 的机器可继续使用官方 [Lark CLI](https://github.com/larksuite/cli)，并提供相应的 `lark-base`、`lark-doc`、`lark-drive` 和 `lark-shared` 技能；保持本人 user 身份。既有 CLI 验证使用 Lark CLI 1.0.94、Python 3.9.6，不代表新增网页途径已通过真实验证。

`skills` 只安装 Skill 子目录。正式发布后，新建当前标准模板可下载 [v1.4.1 完整包](https://github.com/jarlor/lark-dev-workflow/releases/download/v1.4.1/lark-dev-workflow-v1.4.1.zip)，解压后保留其中的 `template/`。CLI 接入时将实际 `template/schema.json` 路径交给 `onboard.py --contract`；网页接入则按实际结构核实并保存候选映射。仓库克隆也包含同一目录。首次绑定旧副本应核对它原来的模板版本、契约与实际字段，不默认套用最新契约；来源不明时保留只读发现结果并说明缺口。模板独立保存，安装 Skill 不会自动登录飞书或生成项目配置。

## 开始使用

1. 打开[公开飞书模板](https://qa2vxy8qipi.feishu.cn/base/O2Tjbsrt7a1XorsQ9O1cKbtJnWg?table=tblmruIMSZp7rVPw&view=vewOKMstkv)，按页面提示登录并点击「使用该模板」，生成自己的研发工作区。也可让 Agent 按发布包的 `template/schema.json` 和两份 XML 在你有权限的空间创建空模板。一个副本可管理多个项目；业务数据写入自己的副本，母版保持为空。实际使用仍遵循飞书账号与租户策略。
2. 按上面的安装方式安装已发布的 Skill，保留独立的 `template` 目录。选择已有 CLI 用户 profile 或本人网页；凭据留在原工具或浏览器中，不写入项目文件。首版网页 helper 只读已有 Base-only 项目，不能用它完成下方的新项目初始化。
3. 把副本链接交给 Codex，说明本次创建或接入哪个项目，以及已有维护约定。已有项目直接绑定 06 中的真实记录；新项目在已授权的接入范围内初始化。

可直接附上实际副本链接并使用：

> 使用 $lark-dev-workflow 接入这个研发工作区，在其中创建“新产品研发”项目。这个 Base 以后还会管理其他项目。本项目由我确认范围，正式记录由我授权的当前 Codex 维护，独立验收按实际执行者关系判断。完成项目记录、两份项目文档章节和反馈项目选项的初始化，将本项目绑定保存到当前工作区；保留其他项目。

初始化先创建 06 项目行，读回真实 ID 和自动编号，再建立两份项目章节、回填真实章节链接，并同步“反馈项目”选项。Agent 从选定项目行定位文档，不凭 Base 中同名文档猜测。已明确的接入授权无需重复确认；只读检查不会初始化远端资源。

日常查询按 project ID 过滤，并核对关联链和目标版本。其他项目的合法视图可以共存，不要求每个项目都先建一套专属视图。07 版本按项目可选；短需求、短测试用表格和原始证据即可，长范围、多截图或复杂证据才写项目文档章节。

## 评论与多人接手

评论处理从本项目的真实记录和绑定文档项目节开始，读取完整线程与回复分页；首次全面对账包含已解决评论，后续对账同源编辑和解决状态变化。先核实作者、项目和适用修订，再正式回写并回读；原线程回复按已有授权执行并去重。评论解决和业务完成分别判断，本地采集记录不替代共享 Base 查重。详见 [评论闭环](skill/lark-dev-workflow/references/comments.md)。

多人协作复用 03 的单用户负责人、状态和进展。项目允许自领或已有分配适用时才接手，其他人占用不覆盖，阻塞／暂停不自动释放，也不按更新时间抢占。交接保留双方真实身份、决定、产物与剩余边界，确认后更换负责人，原执行者停止推进交出的范围。本人操作显式使用已核实的 user 身份；不把项目负责人、代录人或测试者自动当作工作负责人。详见 [轻量协作](skill/lark-dev-workflow/references/collaboration.md)。

两项流程沿用项目原有治理和已授权范围。普通使用不安装定时任务；Linux 定时入口由用户单独启用。

## 只读绑定与实际验证

CLI 途径的 `onboard.py` 只读发现资源，通过 `--contract` 接收独立模板的 `schema.json`，生成项目配置和检查报告；当前参数见 `--help`。它不借用浏览器登录、不创建项目、不改表或视图、不启用表单。网页途径按 [首次接入](skill/lark-dev-workflow/references/onboarding.md#发现绑定与检查) 核实真实结构和项目，另存候选映射。需要初始化时，Agent 仍按用户已授权的范围使用可用工具完成，再核对实际结果。

报告的 `ready` 表示结构绑定检查通过，`validation_level=structure_binding`、`write_access_verified=false` 不证明真实写入或完整业务流程已通过。离线快照的检查结果只适用于该快照，远端写入前仍须核实相关当前结构。

母版反馈表单保持停用。副本先检查共享状态；在已授权的独立副本演练中，先设邀请访问、要求登录、禁止匿名，最后启用。`onboard.py` 只报告这些状态，不会自动更改。提交有演练标识的反馈后，必须回读实际记录核对内容；提交成功回执不替代回读。

## 模板与升级

本包模板规范为 `1.2.0`，绑定格式为 `2`；在线母版位置及发布信息见 `template/release.json`。旧格式 `1` 的项目配置继续可读，不要求迁移现有台账。

GitHub Release 固定每次发布的 Skill、模板契约与完整包；在线模板提供可复制入口。Skill 版本见 `SKILL.md` 的 `metadata.version`；模板结构版本以 `template/schema.json` 的 `template_version` 为准，标题仅用于展示。Skill 与模板可分别升级，使用时核对所选 Release 的兼容说明；“07 版本”记录的是自己的业务项目版本。

2026-11-04 将在线标题从 `v1.0` 对齐到 `v1.2.0`，并补齐飞书与 GitHub 的双向入口。本次为名称和说明修订，未改字段、状态或脚本。已发布的 `v1.2.0` 标签、ZIP 与校验值保持原样，包中的旧展示名称是发布时快照；后续规则修复随新版本发布。

`v1.2.1` 修复将内部核实误建为研发项的问题：受理、查日志、补证和对账回写原项，不单建 DEV；实际研发关联适用需求／Bug，明确授权的独立维护按项目约定处理。本次模板结构和绑定格式未变，已有 Base 无需迁移。

`v1.2.2` 增加面向人的写作规则：提问、事项标题、说明、评论和回报用具体、易懂的语言，保留重要条件、原始反馈和真实编号。仅更新 Skill 与发布说明，模板结构及线上内容不变。

升级先核对差异。Skill 不按新模板自动改造已有项目，不更改现有维护约定。刷新只更新可发现字段并保留人工扩展；资源身份、类型或维护责任冲突时，保留原配置并报告差异。

更多用法见 [模板使用说明](template/使用说明.md) 和 [首次使用示例](examples/首次使用示例.md)。

## 验证工具

在本目录运行 `python3 -m unittest discover -s tests -p 'test_*.py'`。离线测试检查发现、字段、关联、项目范围、分页和配置保护，不访问业务台账。

实际模板与副本验证记录见 `验证结果.md`。示例数据只承载演练，不作为真实产品验收或生产发布依据；结构、读流程和写流程分别报告。

原有结构与绑定测试不自动覆盖新增评论处理或多人接手。新增检查分别说明采集、去重、回写与交接的实际覆盖；单账号演练不能宣称两个真实账号的并发接手已经验证。
