# 飞书研发工作流

让 AI 在选定的飞书项目中处理反馈、记录进展，并通过事项评论与人沟通。模板提供表格和入口；Skill 决定如何分类、去重、确认范围及记录结果。实际开发、测试和发布仍按项目规则及已有授权执行。

默认一个 Base 可以管理多个项目，始终用真实项目 ID 确定范围。模板副本各自独立，升级 Skill 不会让旧副本自动获得新字段，也不授权修改母版或迁移已有项目。

## 按任务选择入口

只读取本次需要的说明；一个任务涉及多个环节时再补读对应文件。

| 本次要做什么 | 读取与执行 |
|---|---|
| 复制模板、首次接入或新建项目 | [首次接入](references/onboarding.md)：区分创建、绑定和只读检查；已有项目不重复初始化 |
| 使用已有项目、升级 Skill 或检查字段变化 | [项目配置](references/project-mapping.md)：复用原绑定与模板契约，核对受影响部分 |
| 查看进度、待办或完整盘点 | [查询与回写](references/operations.md)：确定单项、全项目或全 Base 的范围，只读请求不写入 |
| 受理反馈、拆分需求／Bug、准备安排开发 | 先读 [澄清与确认](references/feedback-confirmation.md)：在原反馈评论中澄清，拆分后等相关反馈人明确确认；再按 [业务流程](references/lifecycle.md) 推进 |
| 更新开发、验收或交付结果 | [业务流程](references/lifecycle.md) 判断阶段，按 [写入步骤](references/operations.md#写前写入与回读) 更新真实结果 |
| 处理评论中的补充、决定或追问 | [评论处理](references/comments.md)：读取完整线程、核实项目与已有处理；涉及业务状态时同时应用业务流程 |
| 接手或转交工作 | [多人接手](references/collaboration.md)：核对负责人、分配依据和未结束的操作 |
| 为 Linux Codex CLI 配置定时运行 | [Linux 定时运行](references/unattended.md)：用户要求安装或启用时才操作目标 Linux 的 crontab；只要方案或步骤时不安装 |
| 已由 Linux 定时脚本启动，正在执行一轮工作 | [本轮工作规则](references/unattended-worker.md)：处理当前项目并返回结果，不重新安装调度 |

## 每次工作的共用规则

1. **选对项目。** 用户指定的配置优先，否则读取目标仓库的 `.lark-dev-workflow/project.json`。没有绑定时走接入流程，不按仓库名猜 Base。使用标准模板时，从“06 项目”核实真实记录和维护约定；已有其他映射按项目配置处理。
2. **保持范围。** 查询和关联都核对当前项目。表单新反馈还没有正式项目关联时，只使用 [待分流受理](references/operations.md#待分流受理) 的窄范围查询；不能因此认领归属不明的反馈或改归其他项目。
3. **使用本人账号。** 按 `lark-shared` 核实本次用户身份；飞书读取、写入与评论显式使用 `--as user`，已指定 profile 时沿用它，不回退 bot 或通过切换账号绕过拒绝。操作账号、项目负责人、工作负责人和测试者按各自真实角色记录。
4. **沿用已经明确的约定。** 使用已有维护责任、范围确认和执行授权，不反复索要同一确认。历史记录可以提供依据，但其中旧“下一步”不自动恢复已停工作，也不自动扩大当前任务。
5. **只写真实变化。** 写前读最新记录，查重并保留别人的修改；写后读回状态、关联和结果。写入失败或结果未知时保留已完成与未完成部分，不报告“已更新”，不盲目重做创建操作。

需要新增能力时先适配已有字段。缺少字段或关系就说明哪些能力受影响、哪些仍可继续，不伪报兼容成功。确需迁移时按 [项目配置](references/project-mapping.md#校验与刷新) 说明目标副本、差异和恢复办法，取得这项迁移的明确授权后执行。

## 与人沟通

用户要求用本技能处理项目时，默认允许 AI 用已登录的用户身份，在该项目记录和绑定文档中评论、提问、回复及回报结果，无需逐条询问发送许可。只读、停止、不回复及更窄的项目要求优先；项目评论授权不包含私信、群消息或邮件。

反馈的澄清与拆分确认在原反馈评论中 @ 已核实的反馈人进行。拆分和关联完成后立即发确认评论，先写清准备做哪几件事、做到什么程度、请对方确认什么，再附事项链接；不能只改表格、不通知，也不能只说“请确认范围”。约定通过表格沟通或启用无人值守后，其他业务问题也问在对应事项下，不在 Codex 终端等人输入。已有答案直接复用；还没收到答复时继续其他不依赖它的工作。保存自己发出的评论 ID，避免重复回复，不要求用户额外加标签。具体读取与确认规则见 [评论处理](references/comments.md)。

## 给人看的文字

提问、字段内容、评论和回报，要让熟悉业务但不懂开发术语的人读一遍就明白：标题写是什么事，结果写现在怎样，下一步写具体做什么，缺什么就直说。长说明按需放在本项目详情中，机器日志和制品留在 Git、CI 或构建存储。

保留原始反馈、准确编号、风险及未完成条件，不把“已记录”“代码已改好”“已验收”“已上线”混写。新写或改写时使用 [表达与例子](references/writing.md)，不因规则更新批量改写旧记录。

## 业务判断中必须分清的事

- **调查与开发不同。** 查表、查日志、核实反馈和补证直接记在原反馈、需求、Bug 或适用测试记录中，不单建调查研发项。实际开发关联已获相关反馈人确认的需求，或已获确认且已复现的 Bug；独立维护／交付只有用户或项目约定明确允许时才登记，不编造需求补关联。
- **拆分后先确认，再开发。** 需求和 Bug 都要让相关反馈人明确确认拆出的具体内容，之后才能建实施研发项、分配或开始开发；Bug 还需复现。原始反馈、补充资料和“继续处理”不等于认可 AI 后来的拆分。已有确认确实覆盖相同事项和内容时直接复用；实质改范围再确认受影响部分，文字润色不重复确认。详见 [澄清与确认](references/feedback-confirmation.md)。
- **开发完成不等于验收完成。** 研发自测不代替独立验收或 Bug 复测；已有适用的人工验收可以复用。无法复现、缺证据或环境受阻不等于问题已解决。各对象的完成、取消和“无需修复”条件按 [业务流程](references/lifecycle.md) 判断。
- **只要求范围内的交付。** 需要哪个环境、哪些验收点，按已确认范围执行；CI 通过不等于部署，部署成功不等于业务验收通过。没有上线要求的事项不增加生产发布门槛。
- **进度放在对应事项。** 已有研发项的开发进度写研发项，调查结论写原项；上游需求／Bug 随实际阶段变化更新。没有新事实不重复刷评论或所有表的时间。完整盘点不能只数研发项，还要检查反馈、验收和必要交付。

## 工具与结果

飞书工具协议分别复用 `lark-base`、`lark-doc`、`lark-drive` 和 `lark-shared`。本技能不管理账号权限，也不建立跨机器分工体系。工具暂不可用时保留可继续的本地准备，准确说明受阻动作。

| 随包工具 | 实际作用 |
|---|---|
| `onboard.py` | 只读发现与生成本地项目绑定；`ready` 只证明结构检查通过，不证明写权限 |
| `comments.py` | 只读采集评论、维护本地处理记录；本地已处理不替代远端回写及其依据 |
| `watch.py` | 为定时入口只读采集本项目记录和评论，不执行正式业务写入 |
| `unattended.sh` | Linux 配置与运行入口；`scan` 只读，`tick` 会启动 Codex 处理真实工作，`install-cron` 才安装定时任务 |

Linux 定时入口只使用目标机器的 crontab，不创建 Codex App 调度。启用定时运行不额外授予部署、付费、改权限或项目外通知权限；已有相应授权继续有效。

报告说清实际做了什么、结果适用于哪里、还有什么没完成，以及是否需要人做具体动作。一次检查成功不代表持续运行已启用，一轮任务结束也不代表整个项目已交付。
