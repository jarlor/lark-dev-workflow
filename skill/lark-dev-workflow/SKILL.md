# 飞书研发工作流

管理业务状态、关联和完成依据。默认一个 Base 管理多个项目，每次按选定项目的真实 ID 工作。模板提供表、字段、表单、原生关联、日常视图和文档容器；Skill 负责分类、去重、修订确认、证据判断和回写。模板不会自动作出这些业务判断。

## 给人看的文字

所有由 Agent 新写或改写的提问、事项标题、范围说明、验收要求、评论、文档、进度与交接回报，都以熟悉业务但不熟悉开发术语的人为默认读者，让对方读一遍就知道发生了什么、需要决定什么。

- 用具体对象、动作和结果表达。标题点明哪里有问题或要增加什么，例如“上传图片后看不到预览”；避免只写“状态治理”“能力闭环”等抽象概括。优先沿用用户和界面已有称呼，必要术语第一次出现时用一句话解释，不另造一套名称。
- 提问先说明相关场景，必要时给一个短例子，再问需要决定的事。选项直接写选择后的不同结果，例如“各自设置时间”与“共用同一时间”，不让人只选字母、术语或猜技术后果。只问仍未明确且影响行为的问题；通俗改写不使已有确认失效。
- 说明和评论先写实际结果、影响和下一步。把“幂等”“调度粒度”“候选构建”“AC 快照”等按当前场景解释成“重复点击也只执行一次”“各自设时间还是共用时间”“准备给大家检查的测试版”“这次约定要做到哪些事”；这些是表达例子，不是机械替换词表。读者理解专业词且它有助于准确判断时可以保留。
- 验收要求写成能检查的行为，例如“连续点两次提交，只新增一条记录”。技术细节、完整错误和证据放到适合的说明或链接中；需要人处理时，说清谁要做什么以及会影响什么，不只写“需确认边界”。
- 通俗不等于省略重要条件。保留影响范围、代价、风险、未完成部分和不确定性；分别说清已记录、已修改、已测试、已上线，不把“还没查清”说成“没有问题”，不添加没有依据的结果。
- 保留原始反馈、引用和确认原文；另写容易懂的整理说明。已有字段名、状态值、业务编号、版本、错误码与机器标识按真实值保存，解释其含义，不为好读而改结构或编号，不因写作规则更新批量改写历史记录。发出或写入前检查：读者能否说清是什么事、现在怎样、是否需要自己做什么。

## 入口与范围

| 用户意图 | 操作 |
|---|---|
| 复制模板、首次接入、创建或绑定项目 | 读取 [首次接入](references/onboarding.md)，在已授权范围初始化项目；只读检查不写远端 |
| 使用已有台账、表结构变更后校验绑定 | 读取 [项目映射](references/project-mapping.md)，复用已有配置并校验受影响部分 |
| 看某项进度、查看所有待办 | 只读核对与报告；完整盘点使用 [operations](references/operations.md) 的盘点流程 |
| 受理新反馈、补充信息或确认范围 | 查重、分类、记录来源，建立或补齐承接关系 |
| 处理评论、回复、评论中的确认或补充 | 按 [评论闭环](references/comments.md) 核实范围、作者与完整线程，再去重回写 |
| 接手工作、分配负责人或交接 | 按 [轻量协作](references/collaboration.md) 核实身份、已有分配与当前占用 |
| 更新研发、测试或发布结果 | 核对事件证据，按最小关联范围回写 |
| 修正错误关联、旧摘要或漏记回报 | 修正台账；不据此推断新产品缺陷 |
| 处理业务事项 | 本技能管理台账；实际研发、测试、部署按项目规则和已有授权执行 |

“查看”不扩展成写入或执行；接入新副本不改模板原本或其他项目。

接入报告的 `ready` 仅表示结构绑定通过，`write_access_verified=false` 仍表示未验证真实写入。模板母版反馈表单保持停用；脚本只读报告副本共享状态。副本表单启用与提交属于另行执行的远端写操作，按 [首次接入](references/onboarding.md) 的已授权演练范围处理。

1. 优先使用用户指定的项目配置；否则读取目标仓库的 `.lark-dev-workflow/project.json`。没有配置时按项目映射确定目标，不按仓库名猜 Base。
2. 从“06 项目”核实真实项目记录与维护约定；普通查询按项目 ID 过滤，关联链和目标版本也核对归属。表单新反馈尚无正式关联时，仅走 [待分流受理](references/operations.md#待分流受理) 的窄范围查询；不遗漏入口，也不认领未知项目。其他项目的合法视图不妨碍本项目工作。
3. 按 [业务流转条件](references/lifecycle.md) 判断阶段；不要重放旧回报里的“下一步”。
4. 发生应回写的事件时，执行 [事件回写与盘点](references/operations.md)，报告实际变化和剩余工作。

飞书操作复用可用的 `lark-base`、`lark-doc` 和 `lark-drive` 技能：分别处理 Base、文档正文和评论。它们负责工具协议，本技能负责业务语义。工具不可用时保留可继续的本地准备，不将安装本技能视为登录、权限或业务写入授权。

`onboard.py` 和 `comments.py` 只读远端并维护本地结果；正式业务回写、评论回复和解决由 Agent 按既有授权另行执行并读回，不能把本地 helper 成功当作远端已更新。

本人操作全程显式 `--as user`，以已核实的真实用户身份为准，不回退 bot。项目负责人、03 工作负责人、代录人和测试者分别记录；沿用现有项目治理，不新增统一单写或自动调度要求。

## 事项路径

- **需求或范围变化**：原始反馈 → 目标、范围和可检查验收标准 → 确认适用修订 → 研发 → 验收。唯一且明确的执行指令本身可以是确认；记录依据，不重复索要固定口令。实质范围变化才使旧确认失效。
- **Bug**：明确预期与异常 → 适用复现依据 → 修复 → 候选构建 → 独立复测 → 关闭。非缺陷、重复、撤回或明确决定不修复可有据标为“无需修复”；无法复现不能据此结束。
- **独立维护、数据或交付工作**：只有用户或项目规则明确将其作为具有独立交付物的业务工作时，才按该约定登记并关联真实来源；“处理反馈”“继续推进”等总体指令不构成这一例外，不为登记编造需求或 Bug。
- **重复、咨询、补证据、台账纠错**：直接关联、答复或修正相应记录，不强制走完整研发链。
- **发布**：按适用交付范围记录具体环境的实际结果。部署成功与产品验收是不同事实。

反馈受理、查表查日志、核实当前行为、复现前调查、补证和台账对账是 Agent 的处理步骤，结论回写原反馈、需求、Bug 或适用测试记录；不因涉及多条反馈、耗时较长或需要跟踪就单建研发项。研发项默认承接已确认需求或已复现 Bug 的实际开发工作，并关联真实记录；项目要求研发项必须关联需求／Bug 时，独立维护也不能绕过该规则。

其他小步骤留在当前任务清单。只有可独立承接、验收或追溯的业务工作才拆记录；一次真实测试可以验证多个事项。

## 完成依据

| 对象 | 完成依据 |
|---|---|
| 反馈已转办 | 有真实承接项与处理摘要；不表示问题已解决 |
| 研发已完成 | 约定交付已提供并完成核对；未覆盖的验收或发布有明确承接 |
| 需求已验收 | 适用修订的必要验收点满足，剩余范围已处理且可追溯 |
| Bug 已关闭 | 同一异常的修复在适用构建上通过独立复测 |
| Bug 无需修复／工作或交付已取消 | 有明确原因和决定依据；不表示修复通过，已有事实与失败历史保留 |
| 测试通过 | 仅证明本次明确范围、方法、环境与构建的结论 |
| 发布已完成 | 指定环境的代码部署或数据／配置交付已验证 |
| 项目／版本已交付 | 约定范围内必要子项、验收和交付均满足 |

只按适用验收范围判断是否需要生产发布；不增加隐含完成门槛。研发自测不代替独立验收；已有明确、适用的人工验收应复用。

## 操作约束

- 保留反馈原文、来源、编号、失败历史与暂停决定。完全重复才归并，范围不同只建立关系。
- 状态由事实推动，回报文字是待核实来源；一项通过不使整条业务链自动完成。
- 日常进度写研发项；反馈转办后不每日同步，需求／Bug 只更新业务阶段，项目／版本摘要随里程碑变化汇总。原生双向关联只写一端。
- `等待前置` 对应真实未完成依赖；环境、数据或服务障碍用阻塞。需人动作时写一个具体请求，常规调查与补证继续由执行方推进。
- 盘点包含历史未收口和停止／暂停事项，但历史状态不自动授权恢复执行。
- 短需求、短测试用表格和原始证据即可；长范围、多截图或复杂证据才写章节。从选定项目行解析文档 URL 与真实锚点，只操作该项目章节。机器产物留在 Git、CI 或构建存储。
- 沿用项目已有维护边界与授权；本技能不附带账号切换、权限管理、调度、定时任务、部署、付费或外部消息授权。

报告涉及编号、实际变化或发现、证据及适用环境、未完成部分和下一步。写入未确认时明确说明，不报告“已更新”。
