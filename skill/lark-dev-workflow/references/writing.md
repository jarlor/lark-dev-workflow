# 给人看的文字

所有由 Agent 新写或改写的提问、事项标题、范围说明、验收要求、评论、文档、进度与交接回报，都以熟悉业务但不熟悉开发术语的人为默认读者，让对方读一遍就知道发生了什么、需要决定什么。

- 用具体对象、动作和结果表达。标题点明哪里有问题或要增加什么，例如“上传图片后看不到预览”；避免只写“状态治理”“能力闭环”等抽象概括。优先沿用用户和界面已有称呼，必要术语第一次出现时用一句话解释，不另造一套名称。
- 表格里每个给人读的字段都用直接、日常的说法。标题说清是什么事，处理结果说现在怎样，下一步写接下来做什么，阻塞原因写具体缺什么。一个单元格先写一句关键事实，较长依据放详情链接，不把内部操作过程塞满表格。不要只写“推进闭环”“对齐口径”“沉淀证据”；例如“开展差异定位与证据闭环”写成“查清两次结果为什么不同”，“候选交付已形成，待独立验收”写成“代码已改好，还要由另一位执行者检查”。例子按真实进展使用，不为简短而省略未完成部分。
- 提问先说明相关场景，必要时给一个短例子，再问需要决定的事。选项直接写选择后的不同结果，例如“各自设置时间”与“共用同一时间”，不让人只选字母、术语或猜技术后果。只问仍未明确且影响行为的问题；通俗改写不使已有确认失效。
- 评论先判断是否有必要发：能否回答对方的问题、请他补充或确认、让他知道有用的结果或变化。只是内部记账、分流、查重或检查完成时，不机械发“已记录”回执。必要的澄清、拆分需求／Bug 后的确认和项目要求的通知仍要发送；不把少打扰变成不回复。
- 说明和评论写与读者有关的结果、影响或下一步，不要求每次三项齐全。内部操作日志、执行约束和事项保留理由留在适合的处理记录里，不整段贴给反馈人；其中确实影响对方使用、判断或行动的限制和风险，要用日常说法讲清楚。把“幂等”“调度粒度”“候选构建”“AC 快照”等按当前场景解释成“重复点击也只执行一次”“各自设时间还是共用时间”“准备给大家检查的测试版”“这次约定要做到哪些事”；这些是表达例子，不是机械替换词表。读者理解专业词且它有助于准确判断时可以保留。
- 身份说明遵守项目约定，不在每条评论末尾机械追加“Codex 代录”等签名。需要说明 AI 代办、原始作者或确认来源时照实说明，不让读者把代录内容误认成新的本人决定。
- 验收要求写成能检查的行为，例如“连续点两次提交，只新增一条记录”。技术细节、完整错误和证据放到适合的说明或链接中；需要人处理时，说清谁要做什么以及会影响什么，不只写“需确认边界”。
- 通俗不等于省略重要条件。保留影响范围、代价、风险、未完成部分和不确定性；分别说清已记录、已修改、已测试、已上线，不把“还没查清”说成“没有问题”，不添加没有依据的结果。
- 保留原始反馈、引用和确认原文；另写容易懂的整理说明。已有字段名、状态值、业务编号、版本、错误码与机器标识按真实值保存，解释其含义，不为好读而改结构或编号，不因写作规则更新批量改写历史记录。发出或写入前检查：读者能否说清是什么事、现在怎样、是否需要自己做什么。
