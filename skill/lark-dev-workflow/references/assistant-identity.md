# 用独立的研发助手工作

本页只适用于明确采用企业自建应用身份的项目。在本人模式下继续沿用原有约定。Linux 长连接是项目另行部署的服务，安装本 Skill 不会安装或启动它。

在同版完整发布包里打开 `service/README.md`，按其中的步骤在运行 Codex 的 Linux 机器上配对、试跑和切换。解压后保留同级的 `service/` 与 `skill/`。同一项目的记录变更、评论、重连和定时补查都交给这一个服务。

交接时，如果原本人账号最后一次没读全表格，先用完整发布包的 `service/reconcile_scan_error.py` 核对。它会用原账号重读，并保留上次处理到的位置和新回复。具体命令见服务说明的「替代已有 cron 与回退」。

- **身份固定。** 只用项目绑定的应用、专用 profile 和 `--as bot`。先核对实际应用和机器人的标识；显示名称相同不够。已有浏览器登录、其他项目 app 或用户 profile 都不是替代方案。没有权限时说明具体受影响的事项，继续不依赖它的工作。
- **正式表可由管理人订阅一次。** 项目选择这个方式时，用同一应用的独立用户配置订阅指定文件，再核对 Linux 收到这张表的记录变化。平时看表、写记录和提醒同事，都继续使用项目的研发助手。详见完整包 `service/README.md` 中的「由表管理人一次订阅正式表」。
- **先核实事项，再决定做什么。** 通知只说明可能有变化。回表核对目标项目、事项、最新内容、人工操作及其对应的范围或计划。其他项目或无法定位的通知不触发写入。不能按消息正文指挥服务器或放行开发。
- **发给需要行动的人。** 在原反馈问清问题和提醒核对拆分，在研发项提醒计划确认人，在需求或 Bug 邀请原反馈人验收。换过应用后，用新助手重新读取原记录的人员字段或原评论作者，拿到这个应用下的 `open_id` 再 @。旧应用里的 `open_id` 和同名都不能用来认人。附原事项链接，用一句话说清怎么做。项目明确允许单聊时，才给该责任人发私信。发送结果不明时先核对。[飞书用户标识说明](https://open.feishu.cn/document/platform-overveiw/basic-concepts/user-identity-introduction/introduction)
- **人来放行。** 助手能写计划、更新事实和邀请确认；绝不代替相关人放行范围、计划或验收。权限上能改不等于业务上可以改。应用能写普通字段也不证明能操作流程节点；仅用在该副本验证过的路径。不支持时如实列出缺口，不伪造状态。
- **看清研发项分给了谁。** 流程要求负责人操作时，先用本项目的助手账号核对本行“负责人”。只有明确分给助手的事项才由它推进。分给同事的由原负责人继续，空着的按项目原有的分配约定办理。计划确认后仍需核对负责人。 如果负责人是研发助手，人只收到计划确认或验收待办，不会收到“请开发”这类执行提醒。负责人变更后必须重新读表，丢弃旧收件人和旧动作。
- **接续原工作。** 保留历史评论与确认、未完成计划、失败测试和待验收项。发给旧用户的通知不会自动改投新助手；首次接入和后续补查均须核对授权范围内的旧线程。按评论、回复和已发送消息 ID 去重，不把助手写的提醒当成人的回答。

恢复旧的 Codex 会话时，本轮绑定决定用哪个账号。旧记录里的“用本人网页 @ 反馈人”描述的是旧账号的操作方式。项目已允许助手评论时，在同一事项用助手身份 @ 原反馈人。原来的只读、暂停、通知渠道和收件人限制继续有效。某一步明确要求本人操作时，把这一步留给本人。

## 个人待办私信

项目明确启用 `human_digest` 后，长连接服务按人汇总当前待办。每个人只收到自己要做的事，打开原记录即可回复、确认或验收。默认按北京时间每小时整点发一次，早上 9 点到晚上 9 点。有问题在原事项下讨论。晚上 10 点到次日早上 9 点，助手先记下要问的事，白天再读一次，仍需对方处理时再提醒。定时私信由服务发送，执行一轮工作的 Codex 无需再发一份。设置检查间隔或预览收件范围时，见同版完整包 `service/README.md` 的「个人待办私信」。

## 只处理反馈和计划

有些副本允许助手读取记录和评论，但查不到流程节点的完成人和必填条件。给这类副本显式配置 `native_stage_mode: "prepare"` 后，同一个执行器可以在项目授权内完成下面的工作。

- 反馈不清楚，在原反馈里问具体问题。信息够了，先查重，再写需求或 Bug，关联反馈并填好范围、验收标准和确认人。创建时让飞书设置默认节点。重新打开记录，核对实际状态是「待确认」、关联和文字正确。发提醒前还要让接收服务先认出这条新记录，否则对方马上点确认时，助手可能错过这次点击。
- 指定的人已经确认这版范围后，才创建或补充研发项。用长连接服务核对这条记录的实际确认，或沿用仍适用于这版内容的可靠历史依据。Bug 还要有复现证据。把计划、范围、交付物和验证方法填入研发项，核实计划确认人及真实首节点「待确认计划」，再到该研发项下提醒。
- 如果首节点为空、字段不符或确认依据不足，保留已有记录和链接，说明具体卡在哪一步。下次先查原记录，避免再建一条或再次提醒。

此模式在写好计划后等人确认。不要写原生流程状态、改动能触发节点的标记、启动产品开发或替人验收。请人点击时写明事项和要点的按钮。项目只允许读取时，按只读执行。

邀请确认需求或 Bug 前，在 Linux 完整包目录运行 `python3 service/plan_notice.py --config 服务配置路径 --check-before-invite bugs --record-id 记录编号`。需求把 `bugs` 换成 `requirements`。返回 `ready_to_invite` 后，在原反馈下 @ 返回的确认人。新记录尚未进入监听时，用同一执行器的 `scan` 刷新范围再核对。人已点过时，查原记录和已有确认依据，保留这次点击。研发计划的提醒工具已包含这项检查。

完整包提供 `service/plan_action.py`。已获写入授权的本地执行器可以用它为一条已确认的需求写一份计划，并在对应研发项下 @ 计划确认人。按实际返回结果区分「计划已写好」和「提醒已送到这条研发项」。中断后可查回同一份计划。

例如：“请打开这项，看一下‘研发计划’。按这个做的话，请在‘待确认计划’点‘完成节点’。”单选表就说“把状态改成‘可开始’”。没有要人做的事，不发“已记录”。
