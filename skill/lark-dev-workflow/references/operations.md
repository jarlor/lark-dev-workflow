# 事件回写、恢复与待办盘点

## 最小关联回写

一次关键事件触发核对，只有事实变化才写字段。不因收到回报就给所有表打一次新时间。

| 事件 | 首要更新 | 按变化检查的关联对象 |
|---|---|---|
| 新反馈受理或归并 | feedback：分类、摘要、承接关系 | 已有需求／Bug／工作项的来源 |
| 范围确认、修订或撤回 | requirements 与稳定详情 | feedback、受影响 work 和旧验证适用性 |
| 复现结论 | verification，bugs 的复现关系和阶段 | 来源反馈、相关需求 |
| 开始、受阻、交付或停止 | work：阶段、交付、下一步 | 来源需求／Bug和反馈；阻塞影响的版本 |
| 独立验收或复测结束 | verification：真实结果及证据 | bugs、requirements、work、delivery |
| 部署或数据交付完成 | delivery：环境、制品、实际结果 | 相关 work、需求／Bug、feedback、版本和项目摘要 |
| 替代方案、确认已有结果、修正误链 | 原记录及真实关系 | 受影响上游摘要与剩余范围 |

既有记录足以承载事件时直接更新，不新增“状态同步任务”。一次事件有多个必要更新时，视作一个可恢复操作，实际 API 不保证多表事务。

日常执行进度集中写 03。反馈已转办后不每日复制研发进度；需求／Bug 只在业务阶段、范围或处置变化时更新；项目／版本摘要在里程碑、必要范围、验收、交付或关键阻塞变化时汇总。结束且无后续动作的记录不需要虚构“下一步”。

05 失败是一次执行事实，保留在失败记录视图；重试新建执行，不覆盖旧失败。当前待推进范围检查有效交付计划或研发项的承接，不能仅统计失败行，也不能把失败改成历史来隐藏待办。

## 待分流受理

表单只提交原始“反馈项目”，新反馈的正式“所属项目”可能为空。项目 Agent 受理入口时，对 00 允许一次窄范围查询：**所属项目为空、反馈项目中的真实编号匹配当前 06 项目、处理状态为待受理或待补充**，三个条件同时成立。先核实原始输入和真实项目记录，再写正式所属项目；此后使用普通 project ID 查询与回写。

“待确认项目”、未知编号或有歧义的输入不由任意项目 Agent 认领，交给已授权的 Base 级分流者，或在报告中列明待定位反馈及具体缺口。已有正式所属项目的记录不进入这个例外；若它与原始输入冲突，保留正式归属并调查，不能借受理查询覆盖已有归属。

## 写前、写入与回读

1. **读取最新事实**：目标记录、需要聚合的子项及新的原始证据；核对本次字段类型和关联目标。证据与旧状态冲突时先解释差异，不能盲信时间最新的摘要。
2. **形成最小变更**：明确每个待改字段的依据。普通单项操作无需额外报告文件；批量或跨多表操作保存紧凑变更清单与原值，便于恢复。
3. **查重及校验关系**：新增前固定稳定记录键。新对象先拿到真实 record ID，再写关联。查询按选定 project ID 过滤，目标须在字段声明的表内；继续核对关联链及目标版本的项目归属。有明确依据的跨项目依赖保留两端归属。原生双向关联只写一端；单向关系按实际方向查询，不机械补写另一端。
4. **按依赖顺序写**：先写需要被引用的记录／证据，再写引用和父项摘要。既有记录仅提交变化字段，保留原来源和未涉及内容。同表批次按工具约定串行，避免并发覆盖。
5. **核对操作结果**：检查退出状态、`ok`、部分成功、忽略字段和警告。字段被忽略不等于该字段更新成功。写后统一读回必要记录；异步落库时允许有限的有间隔重读，不因短暂旧值重复写。
6. **对账并反馈**：核对自动编号、状态、关系、摘要及未完成部分。并发更新时刷新事实后合并；有冲突的字段暂留明确差异，不用旧快照覆盖别人新内容。

创建或写入结果未知时先按记录键／目标 ID 查询。只重试已确认未生效的部分，避免重复创建、重复通知或覆盖已成功内容。

标准模板的配对字段是原生双向关联，写一端后回读反向结果；其他单向字段需要反查时查询实际来源表。适配旧项目确有独立单向配对字段时，按其实际语义维护必要两端并校验目标表。不能把 Bug ID 写入“关联研发项”，也不能把交付 ID 写入“目标版本”。04“关联交付”可在无实际交付时留空，不为源码或 CI 测试伪造交付行。

若一部分写入成功、另一部分失败，保存已完成／未完成清单和当前记录 ID，回报部分完成。不要为了看起来一致而删除真实测试或回滚他人的更新。

## 详情文档按需更新

短需求、短测试用表内说明和原始证据即可。长范围、多截图或复杂证据才追加章节；先从选定 06 项目行取得该项目的文档 URL 与真实章节锚点，核实项目编号，只读写对应项目节。共享容器里的其他项目节不属于本次写入范围；同名文档不能代替该绑定。

需求实质修订保留旧版完整范围、AC 和确认来源；03 的工作范围固定对应 `REQ / rN` 与 AC 快照。可以保留在表内历史快照、原始确认材料或文档修订小节中，但不能覆盖旧内容后只剩版本号。状态留在表中，文档不重复记录每日进度。

## 稳定记录键

先生成并持久化记录键，再发起创建；重试复用同一个键。自动编号与标题不能替代记录键。

- **来源事件**：评论／回复使用真实来源资源类型与 token、comment ID、reply ID，格式固定为 `type:token/comment:comment_id/reply:reply_id`。直接复用采集结果，不加 Base 前缀；Docx 跨 Base 引用也不改变来源身份。键独立于处理人、内容和项目分流，未知→A 或经核实由 A→B 均不改键；同源内容修订另存 hash。写前在共享 Base 查该键，本地水位不提供多人全局去重保证。完整处理规则见 [评论闭环](comments.md)。
- **业务对象**：业务记录键与来源事件键分别保存；有稳定业务对象时以其身份生成，否则生成 UUID 并保存到本次操作清单。业务范围拆分不重造原评论来源键。项目和版本若没有记录键字段，先查可信外部键或已保存的真实 record ID；不能用重名标题自动合并。
- **测试执行**：每次真实执行生成新键，重试写入本次结果时复用；失败后再测试是新执行，不覆盖旧失败。
- **交付执行**：绑定项目、仓库／制品、不可变版本、环境及真实执行 ID；同一构建重新部署保留不同执行依据。无外部执行 ID 时生成并预先保存本次键，不以当前时间重新生成重试键。

恢复时按 `(Base, table, 记录键)` 查询，命中唯一记录才复用其 record ID；多条命中先报告重复与证据，不任意选择或删除。对无法判断是否生效的创建保留未确认状态，不盲目重试。回报接收、正式台账写入和回读确认分别记录，评论提交成功不等于正式回写完成。

## 待办盘点

### 普通单项检查

读取该项、直接上下游、必要的后继构建与相关新评论。项目受理盘点另覆盖上述待分流窄范围，防止漏掉刚提交的表单反馈。只有证据断链、归并链异常或用户扩大范围时才扩展，不顺手盘点整个 Base。

### 全项目或全 Base 检查

1. 先确定全项目还是全 Base。发现实际业务表与对应详情／证据入口，不只用当前视图。完整分页，并记录时间、表、筛选范围和覆盖结果；未读完就不能称“全部”。
2. 对每个业务项同时检查正向和实际反向关系，按业务范围去重。缺归属的记录单列待定位；不能凭标题强行归入项目，也不能默默漏掉。
3. 按 [评论闭环](comments.md) 读取相关完整线程及回复分页；首次全面对账明确包含已解决线程，后续核对新内容、编辑及解决状态变化。识别未登记反馈、漏回写报告和决定；评论状态不代表业务状态，AI 回执不是新需求或人类确认。
4. 对历史失败、旧候选、回滚和后续通过核对适用范围。新成功只覆盖被验证的行为；旧记录保持历史，不能将所有失败测试数当作当前 Bug 数。
5. 不仅检查 work：还检查未承接反馈、待确认需求、开放 Bug、已交付但未验收、已验收但必要交付缺失、项目／版本摘要过时和错误关系。
6. 对存在旧环境或账户阻塞的记录标注观察时间。台账里的旧“不可达／未合并／无权限”不自动代表今天的实际状态；没有执行新核实时不要做当前事实断言。

结果至少区分：

- 当前实际待推进：范围、现有状态、剩余动作和承接者／下一步。
- 等待明确决策或信息：具体需要谁做什么；不将一般调查都推给人。
- 历史未收口与暂停／停止：保留范围、原因、后继关系和恢复条件，不自动执行。
- 证据或台账缺口：误链、漏回报、旧摘要、已关闭但关闭依据待核实；无功能异常证据时不自动变成新 Bug。

按同一业务主项聚合，明确数量口径。反馈、Bug、研发、测试和发布的行数存在重叠，不能相加当作工作总量；“没有新评论”或“研发队列为空”不能证明全项目完成。

## 结束条件与后续

只读任务结束于覆盖范围明确、证据适用性已区分、剩余清单可理解。写入任务还需确认实际变更及未完成部分。

需要回写但工具确实失败时，明确具体失败动作，保留可继续使用的结果，不宣称已更新。已有权限和授权沿用，不将授权管理变成本技能的前置任务。

向外部人员发消息只按用户明确要求或项目已验证的适用通知授权进行；普通台账更新不自动广播，也不创建提醒任务。若发送已获授权，保存实际回执并去重，发送成功不等于对方确认。
