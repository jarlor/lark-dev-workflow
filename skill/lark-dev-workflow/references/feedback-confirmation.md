# 反馈澄清、拆分与开发前确认

处理反馈、从反馈形成需求或 Bug，以及准备安排开发时读取。主流程是：**原反馈中澄清 → 建立并关联需求／Bug → 相关反馈人确认拆出的具体内容 → 安排开发**。Bug 还必须有适用的复现依据；确认与复现互不替代。

## 先在原反馈中问清楚

先看原文、附件和已有讨论，能自己查到的信息由 AI 核实。不清楚用户想要什么、异常发生在哪或希望怎样处理时，将反馈设为“待补充”，在该反馈记录的评论中 @ 真实反馈人，问一个具体、必要的问题。保留原始说明，整理结果写处理摘要；调查和澄清不单建研发项。

反馈人从原始作者、原评论或已核实身份中确定，不能用创建记录的操作账号、项目负责人或代录人冒充。评论使用 `lark-drive` 的结构化 `mention_user` 和真实 open ID，普通文字“@姓名”不算已提及。身份不明确时只核实这一缺口，不猜人、不群发；评论发送成功也不证明对方已读。按 [评论处理](comments.md) 保存回复 ID、读回并防止重复追问。

## 拆分后，请反馈人确认具体内容

信息清楚后按行为和范围查重，建立或补充需求／Bug，并关联真实来源反馈。一个反馈可以形成多个事项；已存在的同一事项直接复用。咨询、完全重复或不需要产品改动的反馈按实际结果答复／归并，不为了流程完整强行建需求或 Bug。

拆分和关联写入成功并读回后，立即在原反馈下发表评论，@ 相关反馈人来确认，不能只改表格就结束。评论先用日常说法写清每件事准备做什么、做到什么程度、哪些不做；再附真实编号和链接，让人能打开查看。短范围直接写在评论中，长内容指向保留了当时版本的详情，同时保留一句看得懂的概括。不要只贴编号问“确认吗”，也不要只写“请确认范围／验收口径／拆分方案”。

例如：“这条反馈整理成两件事：① 增加订单导出，只导出当前筛选结果；② 修复同一订单重复出现，连续导出两次也不能增加订单记录。请确认是否按这两项做；哪项理解不对，请直接指出。”实际发送时 @ 已核实的人，并在每项后附真实事项链接；示例内容只用于说明写法，不能当作实际拆分结果。

评论发出后读回并保存真实评论／回复 ID。发送失败或结果未知时，保留待通知状态，先查是否已经发出，再补未完成部分；不能把“已建项”写成“已请人确认”，更不能因此直接开发。发出前检查：反馈人不打开技术资料，也能说出准备做什么，以及现在需要自己确认什么。

确认按事项分别判断：同一人可以在一条回复中明确同意列出的全部事项，也可以只同意其中一项；只放行已明确确认的部分。合并多个反馈时，核对与本次范围相关的反馈人，各自确认其涉及的内容；已明确授权的代表可以代为确认，但保留该授权依据，不能由 AI 临时指定代表。无关人员和范围外的历史反馈人不增加为确认人。

## 什么才算确认

必须能查到：确认人是谁、何时确认、原回复位置，以及它明确同意的事项与具体内容版本。原反馈描述、补充了复现步骤、AI 自己的整理或回执、点赞、没有反对、超时和“继续处理反馈”等总体指令，都不能自动证明反馈人同意了后来拆出的内容。

相关反馈人针对已展示的拆分内容明确说“这两项按你写的做”等，可以作为确认，不强制口令或再次逐项回复。已有确认覆盖相同事项和未改变的范围时直接复用。实质改变预期、范围或验收要求时，保留旧版与旧确认，重新请相关反馈人确认受影响部分；文字润色或补链接不重开确认。

允许 AI 用用户账号评论，不表示 AI 可以替反馈人批准自己拆出的工作。按已发评论 ID 与实际回复来源核对；身份相同不能把自己的发言当新确认，也不能把同账号的真实新回复一概忽略。项目另有必须满足的确认角色时同时遵守，但不能用其他人的同意替代尚缺的反馈人确认。

## 使用现有字段记录

以下是标准模板的用法，旧副本先核实实际映射；不新增字段或状态选项。

| 位置 | 等待确认时 | 确认后 |
|---|---|---|
| 00 反馈收集 | 澄清时用“待补充”；形成真实需求／Bug 关联后可用“已转办”。处理摘要写“已整理成…，等反馈人确认”；需人介入与下一步写清谁确认哪些项，链接原评论 | 回写确认进展；只在该反馈已无待回答问题时清除相应人工动作。已转办不等于已确认或已解决 |
| 01 需求 | 状态“待确认”，填写需求修订、目标与范围、验收标准；新事项的已确认修订留空。勾选需人介入，下一步指向待确认内容 | 确认依据保存真实作者、时间、原回复和具体版本，已确认修订对应需求修订；其他启动条件也满足后才可研发 |
| 02 Bug | 保留真实处理阶段：未复现用“待核实／待复现”，已复现可以是“待修复”。同时勾选需人介入，下一步写“请…确认按上述问题与修复范围处理”，摘要明确“已复现，尚待反馈人确认” | 确认来源和当时的预期、异常、修复范围及验收要点保存在原评论或已有详情；处理摘要放简短结论与可追溯链接。确认和复现均成立后才可安排修复 |

需求实质改版时保留旧确认历史，但旧已确认修订不匹配新需求修订，不能放行。Bug 没有专用的确认字段／修订号，必须查回摘要所指的原始确认及对应内容；不能仅凭“待修复”、`需人介入=false` 或一句“已确认”放行，也不把复现记录当确认。必要依据无法保存或查回时，继续澄清、调查和整理，暂不安排开发，并报告具体缺口。

## 安排开发前再核对一次

创建研发项、分配开发、接手开始及无人值守续跑前，都核对该项的真实来源、相关反馈人的明确确认及范围是否仍适用；Bug 同时核对复现依据。缺确认时可以读资料、复现和准备待确认说明，不能先建实施研发项、派给执行者或开始修改产品。已有研发项缺依据时保留历史与负责人，核查是否已有有效确认；确实缺失则不新增派工、不继续实施该范围，说明待确认内容。

通过这一步后，再按 [业务流程](lifecycle.md) 登记实际研发、检查依赖、执行和验收。来源是反馈的产品改动不能改叫“独立维护”绕过确认。等待答复不停止整个 Linux 运行器：有其他可继续工作时推进它们，本轮结束后仍可继续则返回 `continue`；全部工作都在等答复时才返回 `waiting`，保留后续检查。

这些条件由 Skill 在执行前检查；现有表格字段本身不提供自动审批或不可绕过的技术锁。
