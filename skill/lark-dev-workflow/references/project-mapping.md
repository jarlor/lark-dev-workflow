# 项目配置与映射

首次选择项目、接入或表结构改变时读取本文件。日常操作复用已验证映射，只核实本次所需资源。

## 配置位置与目标选择

1. 用户指定的配置位置优先；默认读取目标仓库 `.lark-dev-workflow/project.json`。无仓库时使用用户指定的项目配置目录，不写入 Skill 安装目录。
2. 用户明确给出的 Base／项目优先于旧绑定；两者不一致时说明差异，为新目标另存配置，不能覆盖旧项目来消除冲突。
3. 默认一个 Base 管理多个项目。先从“06 项目”核实选定项目的 record ID、真实自动编号和名称，再界定查询范围；不能因名称相似推断归属。用户明确采用整个 Base 专属项目时可保留对应范围。
4. 一个角色有多个可能表、字段或项目且无法唯一定位时，只澄清该歧义。缺失映射留空并报告，不填假 ID。
5. 配置保存结构与责任约定，不保存访问凭据、个人登录 profile、实时待办、节点或调度状态。调用所用 profile 由当前会话或机器配置选择，不进入分发包。

原模板与副本是不同实例。模板版本只是结构约定，不能提供新副本的 table、field、record、option 或文档 ID。

兼容已有 `format_version: 1` 项目映射：沿用其中的 Base、项目范围、表字段、文档和状态别名；它们是已观察到的定位信息，仍需按本次操作核实。不要仅因加载新 Skill 就重写为新版、重新绑定或改动远端资源。

## 逻辑角色

| 角色 | 语义 |
|---|---|
| feedback | 原始反馈、来源、处理摘要和承接关系 |
| requirements | 目标、范围、适用修订及验收标准 |
| bugs | 预期与异常、复现、修复和复测 |
| work | 关联需求／Bug 的实际研发工作；独立维护／交付按明确项目约定，内部核实不单建项 |
| verification | 每次真实验证的范围、方法和结果 |
| delivery | 不可变构建或数据／配置制品在特定环境的交付 |
| projects | 项目归属与整体摘要 |
| versions | 交付批次或产品版本的范围与汇总 |

标准模板采用独立业务表；适配已有项目时可保留其表名、数量与类型字段。项目已有“需求与 Bug 分表”等约定优先。查询同时遵守项目与角色过滤，不能混算同表的不同角色。

缺少项目／版本表可使用已有稳定字段；缺少发布角色不妨碍不含发布要求的需求。按具体能力报告缺口，不要求所有项目先改成模板。不自动建表、改字段、迁移旧值或修复关联。

`project-record` 模式使用真实项目记录。项目专属视图是便利入口，不是绑定的硬门槛；一个共享 Base 可以同时保留 A、B 等多个项目的合法视图，B 的视图不阻断 A 接入。01—05、07 的快速总览显示并按所属项目分组，待处理、需人介入、待验收和已完成类视图供日常查看；视图不替代实际查询过滤。

Skill 普通业务查询明确过滤当前 project ID，读取关联链时继续核对各对象和目标版本归属。00 新表单反馈尚无正式项目关联时，使用 [待分流受理](operations.md#待分流受理) 的窄例外：空正式归属、原始编号匹配本项目、待受理／待补充；核实写入关联后回到普通查询。未知或歧义输入交已授权 Base 级分流者或形成具体待定位报告，已有正式归属不由此覆盖。

跨项目依赖可以存在，但须有明确业务依据并保留两端真实归属，不能为使链路一致而改归项目。脚本只读发现；若本次已明确要求创建／接入新项目，所需初始化按 [首次接入](onboarding.md) 完成，不额外要求重复确认。

07 版本按项目可选，空版本表或无目标版本不妨碍无版本计划的工作；填了目标版本则必须核实属于选定项目。已有项目采用其他稳定归属方式时保留其约定，不据模板自动迁移。

## 项目文档定位

共享 Base 的两份 Docx 默认按项目章节分隔，章节标题使用“真实项目编号 · 项目名称”。06 每个项目行的“需求与 Bug 文档”和“测试与交付文档”链接分别指向本项目的真实章节 URL 与 `#block_id` 锚点；也允许使用该项目独立的 Docx。

Agent 从选定项目行解析文档 URL 与锚点，核实该节标题中的真实项目编号后，只在这个项目节内读写。A 项目行指向 B 项目章节时拒绝该绑定并报告差异。Base 中的同名文档仅是容器，不能据名称替代项目绑定；缺链接或锚点不符时，不能写到文档开头或其他项目节。已有明确初始化授权时可建立并回填本项目真实章节。

短需求、短测试使用表格及原始证据即可，不强制为每项建文档章节。只有长范围、多截图或复杂证据才在本项目节下增加事项章节，保留真实锚点和适用修订。

## 配置内容

- 配置格式版本、稳定项目键与项目名；来自模板时另记模板标识和版本。模板版本与配置格式版本分别兼容，观察时间不是版本。
- 真实 Base token／URL、项目记录或可信过滤条件。
- 角色对应的实际 table ID、名称、必要角色过滤。
- 语义字段键对应实际 field ID、名称、类型；关联字段记录目标表及单向／双向关系。
- 当前可写状态与环境选项；读取兼容旧同义值，不将抽象流程词直接写成新选项。
- 从选定项目行取得的详情／证据文档实际 URL、token、章节锚点与用途；反馈入口和相关视图的绑定。
- 观察时间、来源与校验结果。离线快照应明确标记，不能冒充当前线上检查。
- 维护责任及依据：正式台账维护者、范围确认者、交付回报入口、独立验收约定。可引用项目现有规则，不要求复制人员名单。

首次接入脚本生成 `format_version: 2`：`template` 保存模板 `id` 与 `version`；`base` 保存 `token` 与 `url`；`scope.mode` 为 `whole_base` 或 `project_record`，后者包含真实 `project_record_id`；`tables`、`documents`、`governance` 和 `observed_at` 分别保存映射、文档、责任与观察时间。`governance` 可用 `rules_reference` 引用已核实的完整项目约定，或分别提供 `ledger_maintainer`、`scope_confirmers`、`delivery_report_channel`、`independent_verification`、`feedback_entry`。引用本身不是证据，仍需读取其内容并确认适用；不包含凭据或登录 profile。

机器可检查的字段与能力要求来自随模板交付的结构契约；使用其他 schema 时使用对应适配契约或人工校验映射，不能把不匹配当成自动改表授权。

## 校验与刷新

- 写入前确认相关表／字段仍存在，类型、可写选项及关联目标吻合。可复用当前任务已核实且无变更迹象的 schema；冲突时刷新受影响部分。
- `(base, table_id, record_id)` 才能定位记录。自动编号仅用于显示；单选内部 ID 不跨字段或表复用。
- 标准模板配对关系使用原生双向关联，只写一端并回读核对；其他单向字段按实际方向查询反向记录。旧项目确有两条独立单向字段时沿用其实际语义，不能因同名就假定同步，也不机械写两端。
- 数字前缀不代表资源类型。表、文档、表单和页面使用各自真实 ID 与用途，不因重名猜测。
- 重新发现先生成候选结果，与现有配置对比；只更新可发现字段，保留项目键、维护约定、人工映射与其他人工扩展。结构变更、缺字段或旧资源链接都应显式报告，不静默替换。
- 用户明确要求原地刷新且目标身份未变时，可使用脚本 `--refresh`；其 Base、项目和范围必须与旧配置相同。文档身份同时比较 token 与章节 anchor，同一文档换到另一项目节也算冲突。Base、表、字段、文档的身份或类型以及维护责任发生冲突时，保留原配置并另报差异；不同目标另存配置，不能用刷新跨项目改绑。
- 升级 Skill 不迁移项目数据。配置格式升级、模板升级和业务数据迁移是不同操作，沿用各自适用的用户范围。

## 责任与访问

单人项目和团队项目均可使用；首次接入复用已有责任约定，确实缺失时只确定必要业务角色。未确定正式维护者时可以读取、发现和准备，不自行取得维护权。

多人接手复用项目现有自领／分配约定与 03 单用户负责人，不强制统一单写。06 项目负责人、03 当前承接者、操作账号、代录者和测试者分别识别；自领和交接的具体条件见 [轻量协作](collaboration.md)，评论决定的作者与修订按 [评论闭环](comments.md) 核验。已有规则可通过同一 `rules_reference` 引用，无需为了接手新增一套治理配置。

接入报告必须区分“结构已验证”“维护责任已确定”和“实际写入已验证”。有读取权限不证明可写，协作约定也不等于服务端权限隔离。仅回报权限内结果，不修改 ACL 或账号策略。

若其他协调机制负责分工，本技能只提供业务状态与证据规则。配置中记录的责任人也不是部署、付费或发送外部消息的新授权。
