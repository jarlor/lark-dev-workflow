# 轻量多人接手与交接

使用现有 03 的单用户“负责人”、状态、进展和下一步协调工作，不新增节点调度体系。沿用项目现有分配与维护约定；本技能不要求所有项目采用同一位写入者。

## 区分身份与责任

- **操作账号**：当前已核实的本人 user 身份；飞书调用全程显式 `--as user`，不回退 bot，不修改权限来绕过拒绝。
- **06 项目负责人**：项目层面的责任人，不自动拥有所有研发项。
- **03 工作负责人**：该项当前实际承接者，保存真实用户 ID。当前操作账号可以在已有授权下代录，但代录人和测试者不自动成为工作负责人。
- 人员显示名用于展示，分配、接手和交接使用已核实的真实身份；仅有同名或转述时先核对具体身份。

身份检查沿用 `lark-shared` 的实际协议。当前 `auth status --json --verify` 使用 `identity=user`、`verified=true` 及 `identities.user` 的 ready／valid 状态和真实 open ID，不套用普通 API 的 `ok` 信封。登录核验只证明操作账号；评论作者与人类决定仍按来源单独核验。

## 接手条件

1. 读取 03 最新负责人、状态、范围、交付和下一步，核实真实项目与现有分配依据；同时按 [开发前确认](feedback-confirmation.md#安排开发前再核对一次) 检查相关反馈人确认是否仍适用，Bug 还需复现。交接、已有分配或空闲负责人不绕过这些条件。
2. 项目允许自领未占用工作，或已有有效分配指向本人时，才可接手。其他人已占用不能直接覆盖；需要交接时走下节。
3. 记录负责人不等于已经开始；实际开始执行才进入进行中。先更新必要字段再读回，出现并发冲突时核实有效分配，不反复覆盖来争抢。
4. 阻塞、暂停或长时间未更新不自动释放负责人。不能按过期时间抢占，也不能把没有回复当成同意转交。

读取与回写不是原子锁。多人同时接手出现冲突时，保留当前记录和各方分配依据，只停止冲突部分，按项目既有责任确定唯一承接；不制造额外“已获得锁”的保证。

## 明确交接

交接说明保留原／新负责人的真实身份、交接决定与来源、已完成产物、剩余范围和执行边界。使用原工作项的进展／交接说明及原始决定；长材料才链接必要详情，不能只写“转给某人”。

确认交接决定适用、边界清楚且实际接手成立后，更新 03 负责人并读回。原执行者停止继续推进已交出的范围；在途部署、数据写入或其他共享动作必须先核清，不能因改了负责人就假定旧动作停止。已确认的交接不再重复索要同一批准。

项目既有规则要求特定人确认时沿用其规则；评论中的决定按 [评论闭环](comments.md) 核实原作者与上下文。普通操作账号、转述者或 Agent 回执不能替相关人作出交接决定。

## 完成与记录

完成、取消或转交保留历史负责人、决定与产物；不要为了清空工作队列删除承接历史。无后续动作时不编造下一步；确需人决定时使用“需人介入”并写一个具体请求。

接手不扩展工作范围或授予部署、付费、外部消息等额外动作。已有明确授权继续适用，不因为多人协作增加重复审批。
