# 业务路径与流转条件

这里的阶段是业务语义；实际写值从项目映射选择。用证据判断能否流转，不要求每个事项经过所有阶段或所有表。

新写事项标题、范围、验收要求和确认问题时，遵守 [给人看的文字](../SKILL.md#给人看的文字)：先写用户看到的行为和需要作出的选择，保留适用条件；内部流程术语不直接代替面向人的说明。

## 反馈受理与去重

保留原始作者、原文、时间、来源链接和附件。采集去重使用稳定来源标识（例如评论／回复 ID），业务去重另看项目、预期、异常行为、范围和触发条件。

表单中的单选“反馈项目”只是原始用户输入，正式“所属项目”是受理后核实的关联，两者不是日常重复编辑的同一字段。用输入里的真实项目编号定位“06 项目”的 record ID，核实后写关联；未知、待确认或歧义输入留待分流，不凭名称猜归属。项目重命名保留旧选项历史并按编号识别；项目归档或删除不把旧反馈改归其他项目。

| 分类 | 处置 |
|---|---|
| 新能力、行为改变或验收范围变化 | 进入需求路径 |
| 偏离已有明确预期 | 进入 Bug 路径 |
| 明确作为独立业务交付的维护、数据处理或交付工作 | 按项目约定登记并关联真实来源；反馈处理的总体授权不等于独立业务工作授权 |
| 已有事项的进展、日志、测试或决策 | 追加证据与关联，按事实更新原项 |
| 完全重复 | 关联唯一主事项；保留每条原始反馈 |
| 相似但范围不同 | 保留独立范围并说明关系，不强行合并 |
| 咨询或无需产品改动 | 记录处理结果；无需新建研发链 |
| 信息不足 | 先利用现有资料调查；确有不可自行取得的信息才列具体补充请求 |

“已转办”必须指向真实承接项。“已归并”必须能追溯到唯一主项，不能循环。原反馈含多个可独立验收的目标可以关联多个业务项，不复制成多份相同原文。

收到“已完成”回报时先查当前已有承接关系及证据，不能将回报再登记成新需求，也不能原样把完成结论传播到上游。

反馈转办后保留入口与承接关系，日常研发进度写入研发项；仅分类、归并、承接或最终处置发生变化时更新反馈。

## 需求

1. 固定目标、包含／不包含范围、可观察的验收点和适用修订。短需求可以直接用表内范围、验收标准及原始证据；长范围、多截图才进入项目详情章节。
2. 信息不足为待补充；具体范围未获确认则为待确认。用户已明确要求执行唯一确定的范围时，可直接记录该指令为确认，不强制再回复固定口令。
3. 已有确认仍适用时复用，记录其来源与修订。实质改变目标、范围或必要验收标准时更新修订，并保留旧版的完整范围、AC 和确认依据；不能覆盖旧内容只剩 `r1` 等编号。排版、链接修正和不改变行为的摘要纠错不使确认失效。
4. 范围确认且本项必要前置满足后，按实际开发工作拆分研发。03 研发项固定来源需求编号／修订和该版范围、AC 快照；后续需求修订不自动改写在途工作范围。需求澄清、反馈核实和补证不单独新增研发项，无论调查规模或时长。
5. 交付后按当前适用验收点核对覆盖。缺少必需点时保留待验收或受阻，并写出缺口；全部必要点有适用证据后才已验收。

已有测试可组合覆盖不同验收点，但须说明各自适用的修订、构建和环境。后续构建是否继承通过结果需核对有关变更，不因时间新或分支同名就继承。

只有需求本身包含上线或特定环境交付时，发布才是该需求完成条件。不得给已获确认的验收范围增加隐含门槛。

## Bug

1. 先核实预期与异常。新能力不能为了跳过需求确认而分类为 Bug。
2. 复现证据至少明确行为、条件、预期／实际、环境或代码基线。既有适用测试、日志或源码测试可以复用；不要机械重放线上、付费或破坏性流程。
3. 复现成立后进入待修复。未复现或证据不足保留核实路径，不能当作修复通过。环境阻碍该动作时记阻塞，不虚构复现。
4. 修复交付后关联候选构建，进入待复测。问题发现、复现、修复后复测是不同关系，即使复用同一测试记录也要说明其各自适用性。
5. 独立验证者按修复验收标准对适用构建复测，通过后关闭；失败保留原 Bug，新增此次失败测试记录并回到修复阶段。

确认是非缺陷、重复、已撤回，或有明确决定不修复时，使用“无需修复”终态。摘要必须写清具体原因与依据；重复项的“归并到”指向唯一真实主 Bug，链路不可自指或循环。未复现、证据不足和环境受阻仍保留核实路径，不能作为“无需修复”的理由。这一终态也不能冒充修复通过或替主 Bug 关闭。

独立性来自实际执行者与实现者的关系，不能由“真实 TEST”等标签推断。研发自测不代替独立复测；明确、适用的用户人工复测可以作为独立证据。

已关闭 Bug 缺少关联时，先查已有通过证据并补链。没有证据证明功能回归时，不自动重开或再开发；无法核实关闭依据则明确“关闭依据待核实”，不能伪造通过。

## 研发工作项

创建前核对这是实际开发交付，并关联已确认需求或已复现 Bug 的真实记录；尚在受理、查重、查日志、核实或补证时，结论回写原项，不建“调查／核实／状态同步”研发项。多条反馈可以在本地任务清单合并调查，不能据此新增 DEV。

独立维护、数据处理或交付只有在用户或项目规则明确将其作为业务工作时才按约定登记。若项目要求 DEV 必须关联需求／Bug，遵守这一更严格边界；没有适用来源时不造假项补链，也不把正常核实包装成维护。

至少明确范围、真实来源、约定交付物与验证方式；活动事项填写具体下一步。来源为需求时固定 `REQ 编号 / rN` 及适用 AC 内容。按项目现有字段登记执行者和必要依赖，不引入节点、模型或自动派工配置。

接手与交接按 [轻量协作](collaboration.md) 核对 03 真实负责人和分配依据；实际开始才进行中。阻塞、暂停或更新时间较旧都不自动释放负责人，代录和测试不自动改变承接者。

| 事件 | 阶段判断 |
|---|---|
| 范围明确但尚未开始 | 待处理／待排期，采用项目对应选项 |
| 实际开始工作 | 进行中；计划或已分配不等于已开始 |
| 被另一未完成研发项阻止 | 等待前置，并关联该依赖 |
| 环境、数据、外部服务等阻止当前动作 | 阻塞，记录一个可执行下一步 |
| 已提供约定产物 | 已交付，进入交付核对或待测试 |
| 约定交付已核对 | 本研发项可完成；尚需独立验收或发布的范围继续由关联记录承接 |
| 用户明确暂停、停止或转交 | 保留原范围和产物，记录决定及适用恢复条件 |
| 明确撤销本研发范围 | 已取消；记录撤销原因与依据，保留已有交付和失败 |

研发项完成不能自动关闭关联需求或 Bug。未覆盖的集成、验收或发布应有真实承接记录，不能只散落在聊天中。

部分交付时保留已完成范围和剩余范围。只有可独立负责／验收的新增范围才拆接续项；不要通过拆分或移动遗漏未完成标准。

日常进度保存在研发项；需求和 Bug 只随业务阶段或范围改变更新。完成、取消或其他终态没有后续动作时可清空下一步，不编造待办。“需人介入”仅标明确实需要人的动作，并配具体请求。

## 验证

每次真实执行记录：目的、对象关系、方法、范围／标准、环境、不可变构建或数据制品、执行者、结果及证据。一次执行可以关联多个对象。

- 通过：本次声明的必要检查已满足。
- 部分通过：明确通过与未通过／未执行的边界，不作为整体通过。
- 失败：记录可观察失败，不能通过删标准或换样本消除。
- 受阻：明确哪一步未执行及原因。
- 未执行／待核实：计划或证据状态，不是测试成功。

没有实际执行的新测试不编造日期或结果。复测新建记录并保留旧失败；给旧记录补充真实构建、链接或说明可以原位修正，不算一次新执行。

构建或某个环境确实未知时明确未知。缺少必要的不可变构建身份会限制验收结论，不妨碍保留诊断结果。

04 的“关联交付”指向实际交付记录。源码测试、代码检查和 CI 测试可以只固定不可变源码／构建版本，无实际交付时该关联可空，不为补链接伪造 05 记录。短测试在表内写清标准、结果与原始证据即可；复杂证据才追加项目文档章节。

## 交付与版本

05“交付与发布”的代码发布行标识一个主仓库、一个不可变构建和一个目标环境，保留主 PR 或实际提交、真实部署运行及验证。CI 通过不等于部署。多仓交付拆成可追溯行，并关联同一业务范围；采用版本管理时关联同一版本。

数据／配置交付使用对应外部制品标识、范围和验证／回滚依据；没有程序发布时不编造部署工作流。相同不可变制品在不同环境的交付分别记录。

代码部署成功而必要的数据或配置步骤失败，记部分完成并保留缺口。TEST 已发布不等于生产已发布；版本名称或日期不证明交付。

失败执行保留在“失败记录”视图，不能把旧失败直接当作当前待处理计划。重试是新的执行记录；尚待推进的范围由仍有效的交付计划或研发项承接，已有承接直接复用。不能修改旧失败为历史来隐藏未完成工作，也不能覆盖失败来使列表看起来通过。

明确撤销交付计划时可标“已取消”，保留撤销原因与依据。已经发生的部署、数据交付和失败不可用取消状态抹去，必要时在摘要中区分已发生事实与取消的剩余范围。

07 版本按项目需要使用，可为空；没有版本计划时不为流程完整而创建版本。项目和版本摘要只在必要范围、验收、交付或阻塞等里程碑发生变化时汇总，不复制每日研发进度。

项目和版本摘要由约定范围内必要子项聚合：

- 部分子项完成：更新进展，保留其余范围。
- 已完成要求的验收但未完成必要发布：说明环境差异。
- 发布、数据和验收证据一致且范围满足：才进入对应交付完成状态。
- 新方案替代旧方案：记录替代关系及原范围处置；旧失败保留为历史。

历史“已发布”只说明当时该环境的构建。原文与当前回执冲突时保留两端依据，标记待核实或记录冲突。
