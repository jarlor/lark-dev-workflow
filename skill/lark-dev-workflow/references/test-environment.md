# 测试部署、人工验收与正式交付

项目已有测试环境，或需要把开发结果交给反馈人试用时读取。沿用项目明确的测试分支、部署方式、入口及权限；本节不创建环境、不指定所有项目使用同一种部署工具，也不授权生产发布。没有在线服务的项目按已约定的固定制品验收，不虚构部署。

正常顺序是：开发与自测完成 → 核实目标版本已部署到测试环境 → 建立结果为“未执行”的人工测试项 → 完成必要独立检查并请反馈人验收 → 人确认通过 → 按项目授权正式发布与交付。研发自测、独立检查和人工验收分别留证，不能把其中一种改名充当另一种。

## 先确认测试环境跑的是哪一版

固定本事项需要的完整提交或不可变制品，不只写分支名、“最新”或短编号。涉及多个仓库时固定所需组合；某仓沿用已部署旧提交可以成立，但必须确实满足本事项的依赖。只更新其中一个仓库不自动代表整个组合就绪。

读取项目已有部署状态和当前健康检查，核对实际环境、入口、完整构建标识、部署时间和可追溯运行。项目提供 `test-status.json` 一类状态文件时，先读其真实协议，不凭常见命名假设还有 `version`、`healthy` 或布尔 `ready` 字段。

| 看到什么 | 能得出什么结论 |
|---|---|
| CI／构建成功，或命令输出 `checked` | 检查或制品校验通过，还不能说明已部署 |
| `deploying`／`failed` | 部署未确认完成；列出的仓库可能只是尝试组合，不能当作实际成功运行组合 |
| `ready` | 该次部署曾就绪；还要核对目标构建、时间和当前健康 |
| `unchanged` | 与部署器保存的选择相同，不证明当前健康或功能通过 |
| 状态仍是旧 `ready`，目标提交不同 | 新目标尚未证明已上线；检查实际部署进度，不能推进待验收 |

每次准备验收都保存目标组合和本次观察到的组合。只有两者符合该事项要求、状态确实就绪、当前入口健康时，才把目标部署作为验收依据；部署失败不填测试通过。状态文件没有的信息按项目已有运维证据核实，不编造字段或把运行 ID 猜成部署成功。

沙箱只证明它实际覆盖的功能。通知中简短说明与本次试用有关的限制；模拟交易、合成资料或示例资源不能证明真实外部服务已通过。账号密码、Token 和私有配置留在原受限位置，不写表格、评论、模板或公开仓库。

业务镜像与宿主部署文件分别判断。镜像自动更新不证明宿主配置、代理、初始化脚本或部署器已同步生效；涉及这些变化时，按项目已有维护分工核对来源、应用动作和实际结果。没有证据时明确缺口，不擅自启用自动更新或重启生产。

## 用离线工具核对部署观察

项目的实际状态协议与上述 `environment`、`state`、`repositories`、`deployed_at` 结构一致时，可用 `scripts/test_deployment.py` 核对。它只读本地 JSON，不联网、不部署、不写表；其他协议的项目按真实契约核实，不强改服务来适配脚本。

`expected.json` 保存本次目标，仓库名与健康检查名由项目定义。以下仅为文件结构例子，网址、提交和时间都不是现场证据：

```json
{
  "environment": "test",
  "deployment_url": "https://test.example.invalid/test-status.json",
  "repositories": {
    "api": {"sha": "1111111111111111111111111111111111111111", "workflow_run_id": 101},
    "web": {"sha": "2222222222222222222222222222222222222222", "workflow_run_id": 102}
  },
  "health_urls": {"api": "https://test.example.invalid/api/health", "web": "https://test.example.invalid/health"},
  "max_age_seconds": 300
}
```

`before.json` 是开始前保存的观察。`deployment` 保留实际读取的原始状态；健康结果要分别来自相应接口的实际检查，不能根据 `ready` 猜出 `ok: true`：

```json
{
  "source_url": "https://test.example.invalid/test-status.json",
  "observed_at": "2026-01-01T10:00:05+00:00",
  "deployment": {
    "environment": "test",
    "state": "ready",
    "deployed_at": "2026-01-01T09:00:00+00:00",
    "repositories": {
      "api": {"sha": "1111111111111111111111111111111111111111", "workflow_run_id": 101},
      "web": {"sha": "2222222222222222222222222222222222222222", "workflow_run_id": 102}
    }
  },
  "health_checks": {
    "api": {"url": "https://test.example.invalid/api/health", "checked_at": "2026-01-01T10:00:03+00:00", "ok": true},
    "web": {"url": "https://test.example.invalid/health", "checked_at": "2026-01-01T10:00:04+00:00", "ok": true}
  }
}
```

结束后另读同一组实际来源，保存同结构的 `after.json`；不复制开始快照来假装结束检查。以下命令在 Skill 目录执行：

```sh
# 核对当前部署，使用本次真实采集文件和当前时间
python3 scripts/test_deployment.py --expected expected.json --before before.json
# 核对一次测试前后的构建与部署窗口
python3 scripts/test_deployment.py --expected expected.json --before before.json --after after.json
# 只读重放历史材料，明确核对的是当时的证据
python3 scripts/test_deployment.py --expected expected.json --before before.json --now 2026-01-01T10:00:10+00:00
```

`max_age_seconds` 限制观察和健康检查的新鲜程度，不要求同一候选每隔几分钟重部署。带 `--after` 时开始观察可以较早，但须证明开始时健康检查新鲜；结束观察和健康检查须在本次有效期内。测试期间重新部署，即使提交相同，也不直接视作同一稳定窗口。

退出码 0 表示输入核对通过，1 表示证据不符合目标，2 表示文件或 JSON 无法读取。`ok: true` 只证明给定输入相符，`human_acceptance` 始终为 `not_evaluated`；工具不能验证输入是否真实采集，不能证明反馈人设备可访问、功能通过、宿主配置已生效或人工验收通过。历史 `--now` 重放不能当作当前部署检查。

## 部署后创建待执行测试项

目标测试部署核实后，先在 04 建立或复用本轮人工测试项，结果为“未执行”，再发验收邀请。创建计划记录是合法步骤，不必等人测完才建；邀请、指定人选和部署成功均不是执行结果。必要的独立检查使用自己的测试记录，人工测试项保持未执行，直到反馈人实际检查。

先读该副本的真实字段和选项。标准模板 2.0.0 可复用以下能力，无需为本流程新增字段或改历史状态：

| 现有字段 | 待执行时写什么 | 实际执行后补什么 |
|---|---|---|
| 验证标题 | 一句具体检查内容，例如“检查按日期筛选列表” | 保留本轮对象，不改成另一个测试 |
| 记录键 | 本轮预先固定的稳定键 | 写入重试继续用同一键 |
| 测试目的 | 按对象选择已有“需求验收”或“Bug复测”等选项 | 不因执行者改变而编造新选项 |
| 验证方式 | 按实际计划选择已有“界面操作”“人工核验”等选项 | 核实实际采用的方法 |
| 标准快照 | 明写“类型：人工验收”，关联事项及范围修订、验收点、短操作步骤、拟验收人、入口和必要访问条件 | 保留计划；记录实际执行轮次和范围差异 |
| 环境／构建标识 | 实际测试环境与已核实的完整依赖组合 | 核对测试开始和结束时的实际组合 |
| 执行者／执行时间 | 留空；拟验收人写标准快照，或引用上游已有验收人字段 | 真实执行后填实际执行者及已核实的时间，不用邀请或部署时间代填 |
| 独立性依据 | 没有实际独立执行依据时留空 | 说明实际执行者与开发者的关系；不同标签不证明独立 |
| 结果／结论摘要／验证证据 | 结果“未执行”，结论摘要和实际执行证据留空 | 根据真实执行补结果、现象及可查回证据 |
| 所属项目及对象关联 | 关联真实需求、研发项；Bug人工复测使用“复测Bug”，不写成“发现Bug”或“复现Bug” | 核对关系，保留旧失败的原关联 |
| 关联交付／目标版本 | 有对应实际测试部署时关联真实交付；没有正式版本计划时目标版本可空 | 不为补链伪造正式版本或 Release |

“测试目的”和“验证方式”都是已有单选，不能把“独立复测／人工验收”等执行类型当成新枚举随意写入。执行类型在“标准快照”清楚标注；研发自测、独立复测、人工验收分别记录实际执行者和结果。实际字段缺失时先寻找现有等价能力，不能把未执行写成通过来迁就工具。确实缺必需能力才说明具体差异并按独立迁移授权处理。

## 同一轮补全，新一轮另留记录

创建前固定项目、关联对象及范围修订、执行类型、拟执行者、环境、目标构建组合和本轮执行编号，生成并持久化记录键。标题或当前时间不能替代这份身份；普通 tick 不为同一个未执行计划重新生成编号。

- 同一次计划从“未执行”进入实际执行，补全原 TEST；同一次结果写入超时或回执不明，先按记录键和关联读回，只补缺少内容。
- 拟执行者、范围或目标构建在开始前变化时，保留原计划身份与修改依据，按新的计划身份另行查重；有旧邀请就说明哪份替代哪份，并在原计划的标准快照中记录替代项及“不再待执行”；按项目约定用现有记录性质或查询范围将其移出当前待执行队列。原结果仍是未执行，原身份与标准保留，不能删记录或改成通过。
- 已执行失败、受阻或需要新一轮复测时另留记录；新修复构建使用新轮次。旧失败、旧证据及旧关联保持。
- 同一实际部署可以被多个测试引用，不因每条需求重复建立部署行；部署重试则保留新的执行依据，不覆盖原失败。
- 通知按真实事项、本轮测试、目标构建和收件人去重，保存评论 ID。回执未知先查回，不重发整批邀请。

## 请反馈人试用，保留人的决定

所有必要开发、自测、集成和项目要求的独立检查都齐备，且目标测试部署可用后，AI 才把需求／Bug 推进到“待验收”，在对应事项下说明入口、检查内容及确认方法，并按已有授权通知相关反馈人。原反馈可以发一次简短提醒，链接到同一事项与 TEST，不复制长报告。

不要预先声称反馈人的设备能打开页面。邀请中说明项目已知的访问条件，请对方打开并实际检查；首次核实本人访问是试用的一部分，不能把“本人已经登录”设为创建未执行测试项或发邀请的循环前提。访问失败时按事实记录未执行或受阻并解决具体缺口，不能填人工通过。

例如：

> 这个改动可以试用了。请打开下面的测试页面，选一个日期，看看列表里是否只剩这一天的内容。检查通过后，在需求的“待验收”这一步点“完成节点”；不对的地方请在这里说明。

反馈人对确定范围和构建亲自通过或退回验收节点，可以作为其验收决定来源；AI 保存真实操作记录并复用已明确结论，不再要求人重复确认。人的决定不授权编造未报告的执行步骤、实际测试起止时间或截图；节点确认时间保留为确认来源，不冒充测试开始时间。只有操作者、适用范围／构建不明，或与反馈内容冲突时，才核实具体缺口。AI 自测、CI、部署成功和独立 AI 检查都不能代点人工节点。

测试开始和结束分别核对实际构建。期间相关依赖变化时，保留已执行结果及前后组合，明确哪些结论仍适用、哪些需重测；不能把混合版本结果写成某个固定新版本全部通过。共享测试环境按项目规则协调测试窗口，不默认暂停全部业务、部署 timer 或业务 cron；约定范围外的暂停需要已有适用授权。

人退回时保留失败测试与原验收意见。原范围、原计划内返工沿用仍有效确认；范围或计划变了再确认受影响部分。新修复经自测和测试部署核实后，建立新的未执行人工测试轮次，不把旧失败改为通过。

## 正式发布与交付单独核对

03“已交付”表示该研发项已提供约定产物并完成自测，不表示已上线、已人工验收或正式交付。沿用已有终态及历史证据，在摘要和视图说明中说清“研发完成”；升级不批量改名或重开旧项。当前需求／Bug、测试、交付各自记录真实阶段。

配置了“先测试验收、后正式发布”的项目，反馈人验收通过后，再按已有范围和相应权限推进受保护合并、正式发布及交付。测试分支推送或测试部署本身不创建正式版本／GitHub Release，也不自动授权生产；正式版本按原 07 台账及项目发布约定维护。没有上线要求的事项不额外增加生产门槛。

05 按真实环境记录交付，测试部署与生产部署分别留证。多仓分别记录主仓库、不可变构建和实际部署运行，并能查回完整组合；CI 运行不代替部署运行。只有约定的正式部署和交付检查都成功，才把对应正式交付标完成、汇总项目／版本结果并结束包含发布要求的反馈。失败或部分完成保留实际结果及剩余工作，不能沿用测试环境成功来填正式交付完成。

部署与业务调度各有职责：已有部署服务更新测试容器，项目运行器处理表格和反馈。接入本流程不新增第二个业务写入者、重复 cron 或新的编排服务；环境维护由项目原分工负责。
