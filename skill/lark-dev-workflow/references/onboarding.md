# 首次接入与模板副本

默认一个 Base 管理多个项目。目标是为选定的真实项目建立可追溯绑定与可用入口，同时保持模板母版和其他项目不变。

## 先区分操作

| 本次请求 | 允许的默认动作 |
|---|---|
| 创建一份新的标准模板 | 按独立模板包的定义创建新 Base 及其配套资源；保留新建资源回执 |
| 从指定模板复制工作区 | 复制已指定模板，保存副本回执，再接入其中的项目 |
| 接入新副本／在 Base 创建新项目 | 在已明确的接入范围内初始化 06 项目、项目文档节和反馈选项，再校验绑定 |
| 绑定已有项目或只读检查 | 发现真实项目与资源，校验并保存本地配置或检查报告 |
| 已有项目，刷新映射 | 只读发现并生成差异；保留原绑定和人工约定 |

接入不隐含业务数据迁移或更改源 Base。没有模板链接时先检查项目已提供的模板包或配置；真正缺少目标链接时只询问目标，不能自行选中另一个项目。项目初始化属于用户明确接入／创建该项目的范围，已有授权不重复确认；只读检查不触发初始化。

## 模板作为独立交付物

模板包提供结构契约、字段与状态说明、可复制 Base 的定位信息，以及配套文档用途。它与 Skill 分开升级；Skill 安装目录不保存具体模板发布实例或项目绑定。

### 获取配套模板

优先使用用户或项目已提供的模板包与契约，不用公开模板覆盖项目已确认的结构。通过 `npx skills` 安装时，只会安装 Skill 子目录，仓库中的 `template/` 不会一同安装。

本候选 Skill 为 `1.3.1`，配套模板结构为 `1.2.0`。创建或复制这一版标准模板时，可从已发布的 [v1.3.0 Release](https://github.com/jarlor/lark-dev-workflow/releases/tag/v1.3.0) 下载 [完整包](https://github.com/jarlor/lark-dev-workflow/releases/download/v1.3.0/lark-dev-workflow-v1.3.0.zip)，使用包内 `template/schema.json`。Skill 与模板结构版本分别维护。

首次绑定早已复制的旧 Base 时，先核对它原来的模板版本、配套结构说明和当前实际字段；即使尚无本地配置，也不能直接套用当前 Skill 附带的最新契约。原版本不明或找不到原契约时，保留实际只读发现结果，说明无法核实的能力；可按 [项目配置](project-mapping.md) 人工建立有依据的映射，不编造模板版本、不宣称完整兼容，也不改表来迎合新契约。

将已核实适用于该副本的契约路径传给 `onboard.py --contract`，不要把安装目录下不存在的 `template/` 当成默认路径。Skill 版本与模板结构版本分别记录；已有项目的原契约和映射不会因升级 Skill 被替换。

### 复制与核实

复制使用 `lark-base` 的在线 Base 复制能力。先区分“复制完整模板”和“仅结构”：不要为了获得空业务表而默认丢弃模板内说明。标准模板本身应无真实业务记录；演示数据应在专用演示副本中。

创建或复制结果未知时先根据返回的任务／资源标识和可见资源核实，不重复创建。对实际访问拒绝不更换操作者来绕过；可继续不依赖该访问的本地准备。

## 发现、绑定与检查

1. **固定目标**：解析副本 URL，记录其 Base 身份、模板来源和复制回执。新副本的 Base ID 应与源不同；直接接入已有项目不要求产生副本。
2. **读取实际结构**：发现表与文档目录，再读取相关字段、状态选项、关联目标、视图和反馈表单。名称可用于候选匹配，唯一匹配和类型检查通过后才写入配置；歧义不可自动选第一个。
3. **界定项目**：默认选择 06 中的真实项目记录；已有项目直接复用，新项目按下节初始化。保存真实 project ID、自动编号与名称，业务查询固定 project ID；用户已有明确单项目 Base 配置时可兼容其范围。
4. **绑定配套资源**：从选定 06 项目行解析两份文档 URL 与真实章节锚点，核实章节标题中的真实项目编号并只访问该项目节；A 项目指向 B 节时拒绝该绑定。独立项目 Docx 也可使用。不能根据 Base 内同名文档猜绑定，也不能假定所有外部链接会随 Base 复制自动改绑。
5. **确定责任**：从项目已有约定或本次明确指令记录维护者、范围确认和验收规则。需要回报而无正式写入责任时，只保存回报状态，不声称台账已更新。
6. **保存与反馈**：配置默认写入目标仓库 `.lark-dev-workflow/project.json`；已有配置先输出候选文件并比较，不覆盖未知内容。报告可用能力、缺口和实际验证层级。

`project-record` 模式要求真实项目记录，项目专属视图不是绑定硬门槛。其他项目的合法视图、历史视图和共享总览都可共存；不能因它们过滤 B 而阻断 A。实际操作按选定 project ID 查询，再核对关联链及目标版本归属；有明确依据的跨项目依赖保留真实归属。日常视图用于阅读，不替代范围校验。07 版本按项目可选，不要求为无版本计划的项目新建版本。

使用本技能的 `scripts/onboard.py` 执行只读发现和本地配置生成。先读取 `--help` 核对当前参数；通过 `--contract` 显式传入独立模板包的 `schema.json`，不从其他项目的实例映射推断。入口参数包括目标 Base URL、项目键、项目名、输出路径与项目范围；多项目范围需真实项目记录。Agent 从已有明确指令或项目规则整理 `--governance` 所需责任约定，不要求人填写配置或重复确认；同一绑定刷新可复用原约定。首次确实缺少维护责任时仍可只读检查，报告尚缺内容。当前会话明确指定 profile 时传入命令，保持 user 身份。

`--snapshot` 只用于已获得的结构快照校验或离线演练。输出配置的 `validation_mode=offline_snapshot` 和报告中的 `ready` 只表示该快照结构可绑定；远端写入前仍需核实当前相关 schema。它不能证明当前远端状态，也不能代替真实副本接入验收。脚本检查结构和能力，不替代维护授权、业务证据或完整的文档／视图人工核对。

检查结果写入配置输出路径旁的报告文件，例如 `project.json` 对应 `project.report.json`。存在阻断性结构冲突或维护责任未明确时，只输出报告，不保存活动配置；先处理具体缺口再重新发现。已有活动配置默认保留，使用另一个输出路径生成候选文件。用户明确要求刷新同一绑定时可用 `--refresh`，仅更新本次可发现的字段并保留人工扩展；文档同时比较 token 与章节 anchor。Base、表、字段、文档的身份或类型以及维护责任发生冲突时，保留旧活动配置并另报差异，不自动改绑。

复制验收时，可用 `--source-snapshot` 提供原模板快照，检查副本 Base 和文档 token 是否仍指向源资源。该检查只覆盖所提供快照中的结构引用；正文链接、表单和页面行为仍需按上面的步骤核对。

## 初始化一个项目

在用户已明确要求接入／创建的新项目范围内，按依赖顺序执行；相同请求或超时恢复先查已有记录和章节，不重复创建：

1. 在 06 创建项目行并保存真实 record ID 和平台自动编号；名称不充当项目 ID，也不手造 `PRJ-0001` 等编号。
2. 在共享“需求与 Bug 说明”和“测试与交付证据”容器中分别建立“真实项目编号 · 项目名”章节，取得实际 block ID，再把完整章节 URL 回填该项目行。若用户采用独立项目 Docx，则绑定该项目的真实文档。每个项目预备的是容器章节，不是为所有短事项强制建立详情。
3. 将该项目的“真实编号 · 项目名”同步到 00 单选“反馈项目”的选项中。空母版仅有“待确认项目”；编号来自刚读回的 06 自动编号。表单不使用关联字段作为题目。
4. 按真实项目行重新读取并校验绑定，保存项目侧配置。已有明确责任与范围直接沿用，不重复询问；需要新版本时才建立 07 行并关联本项目。

项目重命名时保留旧的反馈选项值与历史输入，新增或同步当前显示名称；受理仍按稳定编号定位真实项目 ID。归档／删除项目不把其旧反馈转归其他项目。无法唯一定位的输入保持待分流并说明缺口。

## 反馈表单启用与演练

模板母版的反馈表单保持停用（`disabled`），不接收业务或演练反馈。复制后先读取副本表单的真实共享设置；入口和题目存在，不表示表单已启用或用户能够提交。

表单共 5 题：“反馈项目”“一句话反馈”“原始说明”“截图附件”“来源链接”，前三题必填。“反馈项目”是原始输入，提交后正式“所属项目”可能为空。受理入口必须按 [待分流受理](operations.md#待分流受理) 查询本项目编号匹配的未归属待受理／待补充记录，核实后写正式关联，避免只按 project ID 查询漏掉新反馈。

两字段属于不同阶段，不要求日常重复编辑。待确认、未知或歧义输入交已授权 Base 级分流者或报告具体待定位信息；已有正式归属与原始输入冲突时保留正式归属并调查，不从默认视图或当前聊天猜项目。

`onboard.py` 只读查询并报告表单的 `enabled` 等共享设置。报告的 `validation_level=structure_binding` 和 `ready` 仅表示结构绑定检查结果；`write_access_verified=false`、`submission_verified=false` 明确表示脚本未验证实际写入和提交。表单停用时可以保存结构绑定，但必须说明入口尚不可提交。

用户已要求且授权首次接入写入演练时，沿用该授权，仅对自己的独立演练副本执行以下动作；只读接入不会隐含这些远端写操作：

1. 按 `lark-base` 表单共享协议先读取现状，确认实际 Base、table 和 form 都属于演练副本。
2. 逐项设为邀请访问（`invite`）、要求登录（`require_login=true`）、禁止匿名（`allow_anonymous=false`），最后再启用（`enabled=true`）。每次只更新对应设置，不扩大为公开或匿名访问，不改模板母版。
3. 读取真实题目后提交一条明确标记的演练反馈；记录提交回执，再回读副本表中的实际记录核对内容。仅收到成功回执不能报告提交验证通过。
4. 结果未知时先查回已提交记录，不盲目重复提交；按实际结果分别报告共享设置、提交和回读。保留演练标识，未经要求不删除已有记录或更改其他项目。

若需额外授权，只询问尚未授权的具体动作；已经覆盖的同一演练范围不重复确认。对实际权限拒绝保留结构检查结果与受阻步骤，不通过放宽共享或更换身份绕过。

## 首次接入验收

区分三个层级，不把前一个层级宣称为后一个：

1. **结构绑定**：目标身份、项目范围、必需字段与选项、关联目标、文档与入口结构均已实际检查；缺失能力有明确说明。此层级的 `ready` 不证明写权限、表单提交或业务全流程通过。
2. **读流程**：能按新项目范围查看空台账或本项目记录，详情和反馈入口可打开；无源项目记录、旧身份和旧链接混入。
3. **写流程**：仅在用户要求验证写入且已授权的专用副本中执行有标识的最小演练，检查真实创建回执、关联、回读与重复执行查重。保留失败记录和实际测试结果，不在已有项目创建试验业务。

模板发行验收宜覆盖同 Base 两项目的范围隔离、反馈原始选项到真实项目关联、项目文档锚点、需求确认及旧修订快照、重复反馈／Bug 归并、原生双向关联、Bug 失败复测后再次通过、无需修复与取消的有据处置、无交付的源码测试，以及跨表部分写入后的恢复。演练数据必须明确标记为演示，不冒充真实产品复现、验收或发布。

最终报告给出副本链接、配置路径、使用的模板版本、验证范围和剩余缺口。只完成本地候选配置时明确说明；未验证写入能力不报告“全部接入完成”。
