# 飞书研发工作流模板

默认一个 Base 管理多个项目，模板规范为 `1.2.0`，配套 Skill 为 `lark-dev-workflow`。模板母版不保存业务记录；使用自己的副本，在“06 项目”中区分项目。

[使用飞书模板](https://qa2vxy8qipi.feishu.cn/base/O2Tjbsrt7a1XorsQ9O1cKbtJnWg?table=tblmruIMSZp7rVPw&view=vewOKMstkv) · [GitHub 仓库与安装说明](https://github.com/jarlor/lark-dev-workflow) · [v1.2.0 发布包](https://github.com/jarlor/lark-dev-workflow/releases/tag/v1.2.0)

在线名称为 **Agent研发工作流｜v1.2.0**。点击「使用该模板」生成自己的副本，安装 Skill 后将副本链接交给 Agent。模板版本对应结构契约；“07 版本”用于管理自己的业务版本。复制后保留所用版本，更新 Skill 不会自动升级已有 Base。

## 首次接入

1. 复制模板为自己的研发工作区，保留字段、视图、表单和两份文档容器。现有业务台账不作为演练对象。
2. 在项目工作区把副本链接交给 Codex，说明本次创建或接入哪个项目和已有维护约定。已有项目直接核实真实记录；新项目初始化属于明确接入／建项目的范围，无需重复确认。
3. 初始化先创建 06 行，读回真实 record ID 和平台自动编号，再在两份共享 Docx 中各创建“真实项目编号 · 项目名”章节，将真实章节 URL 回填该项目行。也可按项目使用独立 Docx。
4. 将“真实项目编号 · 项目名”同步到 00“反馈项目”单选选项。自动编号不能手造，也不能凭同名项目猜 record ID。
5. 运行只读接入检查，把本项目绑定保存到工作区 `.lark-dev-workflow/project.json` 或明确指定的位置；配置保存真实项目 ID、字段和项目文档锚点。检查只报告差异，不自动迁移业务数据。

共享 Base 的其他项目视图可以正常存在，专属项目视图不是绑定门槛。Skill 的查询始终使用选定 project ID，并核对关联对象与目标版本归属；有明确依据的跨项目依赖保留各自归属。

## 反馈入口

表单有 5 题：“反馈项目”“一句话反馈”“原始说明”“截图附件”“来源链接”，前三项必填。关联字段不作为表单题；“反馈项目”是原始用户输入，正式“所属项目”关联由 Agent 受理后核实写入，两者不需要日常重复编辑。

空母版的项目选项仅有“待确认项目”。项目建立后按真实编号加入“PRJ-0001 · 项目名”形式的选项，示例编号不代表可以手填。未知或歧义输入留待分流；项目重命名保留旧选项历史，按稳定编号定位；归档或删除项目不会将旧反馈改归其他项目。

母版表单保持停用。副本先读取实际共享状态；在已授权的独立副本演练中，依次设为邀请访问、要求登录、禁止匿名，最后启用。提交演练反馈后必须回读真实记录核对内容，结果未知时先查回，不盲目重提。

`onboard.py` 始终只读。报告的 `ready`、`validation_level=structure_binding` 只表示结构可绑定；`write_access_verified=false` 不证明真实提交或业务流程通过。离线快照检查也不证明当前线上状态。

## 表与日常视图

| 表 | 用途 |
|---|---|
| 00 反馈收集 | 保存原始输入与来源，核实项目后分类、查重和承接 |
| 01 需求 | 保存目标、范围、修订、AC 和当前确认依据 |
| 02 Bug | 保存预期、异常、复现、修复、独立复测或无需修复的依据 |
| 03 研发项 | 固定来源需求修订与 AC，记录日常进度、依赖和约定交付 |
| 04 测试与验收 | 每次真实执行的目的、方法、环境、源码／构建、结果和证据 |
| 05 交付与发布 | 记录实际代码、数据或配置在指定环境的交付；测试和生产分别记录 |
| 06 项目 | 真实项目身份、范围、里程碑摘要及本项目文档章节链接 |
| 07 版本 | 项目按需使用的交付批次；没有版本计划时可以为空 |

01—05、07 的快速总览显示所属项目并按项目分组；待处理、需人介入、待验收、已完成类视图帮助查看当前事项。它们不替代实际项目过滤，也不自动证明业务完成。

05 的失败执行单列“失败记录”，不混入待处理计划。重试另建新的执行记录，尚待推进的范围由有效交付计划或研发项承接；不能把旧失败改为历史来隐藏未完成工作。

日常进度只写 03；反馈已转办后不每日同步，需求／Bug 只随业务阶段变化更新，项目／版本摘要在里程碑变化时汇总。“需人介入”只标确需人的具体动作；等待前置必须有关联的未完成研发项，环境或数据阻碍使用阻塞。事项结束且没有后续动作时，不需要编造下一步。

## 评论处理

本项目记录及已绑定 Docx 项目节中的评论可作为反馈、补证、确认或交接来源。Agent 读取完整线程和回复分页；首次全面对账包含已解决评论，后续核对内容编辑、解决和恢复变化。根评论或跨项目评论无法可靠定位时保留待定位，不凭同名引文认领。

每条评论／回复使用独立于处理人的稳定来源键，同源内容修订另记 hash。处理前在共享 Base 查已有承接；原评论修改优先更新原记录并保留旧原文，不重复创建反馈。本地水位不替代多人共享查重。

作者实际 open ID 和项目确认规则都要核验；本人账号的 Agent 代发、演练或回执不算人类确认。先正式回写并回读，再记录处理完成；回复只按已有授权在适用线程进行。工具不支持回复全文评论或已解决线程时，在当前报告回告，不自动恢复线程或改投其他位置。

评论所提问题实际处理完才解决，未完成的线程保留。解决评论不等于需求验收、Bug 关闭或发布成功。此流程按请求执行，不增加监听或定时任务。

## 多人接手与交接

03“负责人”是单个真实工作承接者，06“项目负责人”是项目层面的责任人。操作账号、代录人和测试者分别识别，不自动改成工作负责人。本人操作显式使用已核实的 `--as user`，不切换 bot 或修改权限。

项目允许自领或已有分配适用时才接手。写前读取最新负责人和状态，其他人占用不直接覆盖；实际开始才进行中。阻塞、暂停或久未更新不自动释放，不能按时间抢占，也不能把无回复当同意。

交接记录原／新负责人真实身份、决定来源、已有产物、剩余范围与边界；确认后更新负责人并回读，原执行者停止推进交出的范围，在途共享动作先核清。完成保留历史负责人；已有治理与授权继续适用，不增加统一单写或重复审批。并发冲突需核实有效分配，读取后回写不是原子占用锁。

## 详情和证据按需展开

短需求、短测试在表内写清范围、标准、结果并链接原始证据即可。长范围、多截图或复杂证据才在项目节下增加事项章节，机器日志、代码和制品保存在 Git、CI 或构建存储。

默认两份共享 Docx 按真实项目编号与名称分节。Agent 从选定 06 行解析文档 URL 与真实 `#block_id`，核实项目编号后只读写该项目节；不能靠 Base 中同名文档猜测。独立项目 Docx 也可使用。

需求实质修订时保留旧版完整范围、AC 和确认依据，不覆盖后只剩版本号。03 工作范围固定适用的 `REQ 编号 / rN` 与 AC 快照；新修订不会自动改变在途工作的范围。

## 状态和关联的含义

反馈已转办表示已有承接项；研发已完成表示约定交付已核对；需求已验收表示适用验收点满足；Bug 已关闭需要同一异常在适用构建上通过独立复测。CI 通过不是部署完成，部署成功也不是产品验收。

Bug“无需修复”适用于有据的非缺陷、重复、撤回或明确决定不修复；摘要必须说明原因和依据。重复 Bug 的“归并到”指向唯一主项且无循环；无法复现、证据不足或环境受阻不能据此结束。03 和 05“已取消”需要明确撤销依据，已发生的交付、结果与失败继续保留。

标准模板的十对配对关系使用原生双向关联，只写一端，另一端由平台维护并读回核对；其余单向关系按实际方向反查。04“关联交付”只关联真实交付；源码或 CI 测试无交付时可空，不为补链接伪造 05 行。

## 配置与升级

`schema.json` 描述字段、状态、视图、表单和功能条件；这些结构不自动判断分类、确认、独立性或完成。具体职责见 [模板与 Skill 职责](../模板与Skill职责.md)。

模板版本、配置格式和实际资源绑定分别维护。刷新只更新可发现字段，保留人工扩展；资源身份、类型或维护责任冲突时保留原配置并报告。日常接入不自动删字段、改旧状态或迁移业务数据。

每次创建前持久化稳定记录键，超时重试复用该键。同一次测试或交付回写复用执行键，真正的新执行使用新键并保留旧失败；自动编号仅供展示，实际关联使用服务端 record ID。
