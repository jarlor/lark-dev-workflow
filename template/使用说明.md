# 飞书研发工作流模板

本目录提供模板结构 **2.0.0**。配套 Skill、完整流程图和安装方式见 [GitHub 仓库](https://github.com/jarlor/lark-dev-workflow) 与 [完整流程](../skill/lark-dev-workflow/references/workflow.md)。

[在线模板入口](https://qa2vxy8qipi.feishu.cn/base/O2Tjbsrt7a1XorsQ9O1cKbtJnWg?table=tblmruIMSZp7rVPw&view=vewOKMstkv)是可复制的母版。发布包中的新结构不表示线上已经更新；线上版本以页面及对应 Release 的部署结果为准。先正式发布，再用该固定版本迁移线上模板。母版不保存业务事项，反馈表单保持停用。

## 人和 AI 各做什么

| 环节 | AI 做什么 | 人做什么 |
|---|---|---|
| 收到反馈 | 查重；不清楚就在原反馈评论中问清楚 | 在原反馈下面补充情况 |
| 拆分需求或 Bug | 写清要解决什么、怎样算完成，关联原反馈，设为待确认并通知反馈人 | 查看拆分结果；正确后手动完成待确认节点，进入可研发 |
| 准备研发 | 为每个研发项填写研发计划，设为待确认计划并提醒计划确认人 | 看计划；同意后手动完成该节点，进入可开始 |
| 执行和自测 | 开始后设进行中；完成并自测通过后设已交付 | 有疑问在研发项评论里讨论 |
| 验收 | 所有必要工作完成、结果可以实际验证后，把需求或 Bug 推进到待验收并通知验收人 | 实际试用；通过后完成节点，不通过则写清问题并退回 |
| 结束反馈 | 关联事项均已处理后，在原反馈说明最终结果 | 未解决的部分继续保留 |

Bug 在安排修复前，还要有真实复现依据。开发者自测不能代替必要的独立复测，也不能代替反馈人的验收。评论用于讨论和提醒，不代替手动确认节点。

## 字段怎么用

- **状态**：01 需求、02 Bug、03 研发项使用流程字段。需求和 Bug 为「待确认 → 可研发 → 研发中 → 待验收」，正常结束显示「已验收」；研发项为「待确认计划 → 可开始 → 进行中」，正常结束显示「已交付」。结束名称不是额外等待完成的节点。
- **研发计划**：写准备改什么、怎样做、怎样自测、对使用和数据有何影响。计划完整写在字段里；评论不重复贴长计划。
- **确认人、验收人、计划确认人**：使用真实人员字段。按项目约定确定具体人，不能自动填成操作账号；项目要多人确认时，先收齐所需意见再由指定的人推进。
- **处理情况**：正常、等待前置、受阻、暂停。它保留当前流程位置。等待前置要有真实未完成依赖；账号、环境或资料问题写受阻。
- **修订和确认依据**：放在追溯视图，保存已确认的是哪一版。实质改动要重新确认，旧记录与失败记录保留。
- **需人介入、下一步**：仅用于额外需要人处理的问题，例如「请补一张出错截图」。确认和验收直接看流程，不在字段中堆长段提醒。

标题、计划、范围、验收标准和评论都必须让熟悉业务的人读一遍就明白。写具体动作和结果；必须用技术词时顺手解释。不把查日志、同步状态、内部调度等过程整段发给反馈人。原始反馈和必要限制保留，不为简短而改变事实。

## 表与沟通位置

| 表 | 保存什么 | 在哪里讨论 |
|---|---|---|
| 00 反馈收集 | 原始问题、来源、承接事项 | 原始情况、补充资料、最终答复 |
| 01 需求 / 02 Bug | 具体范围、验收标准、当前阶段 | 拆分是否正确、范围变化、验收结果 |
| 03 研发项 | 研发计划、执行进度、交付结果 | 计划问题、执行中需要的决定 |
| 04 测试与验收 | 每次实际测试的环境、版本、结果和证据 | 测试结果的补充说明 |
| 05 交付与发布 | 指定版本在指定环境的真实交付 | 交付问题 |
| 06 项目 / 07 版本 | 项目身份、约定、交付批次 | 按项目已有约定 |

反馈、测试、交付、项目和版本继续使用各自的单选状态。一个 Base 可以管理多个项目，查询和关联都使用真实项目记录 ID。内部核实、采证、查重不单独建研发项，也不制造假需求来凑关联。

## 首次使用与已有副本

1. 复制线上模板或按本包结构创建空工作区。核对副本的实际版本，不凭母版当前名称猜测旧副本版本。
2. 将副本链接交给 Codex，并说明项目及原有约定。已有项目直接复用；新项目按授权建立项目记录和需要的文档章节。
3. 核对各表字段、流程节点、确认人员和必填规则，再保存 `.lark-dev-workflow/project.json`。结构检查通过不等于写入或完整业务流程已验证。
4. Linux 按 [定时运行说明](../skill/lark-dev-workflow/references/unattended.md) 试跑。保持本人账号，不因缺 CLI profile 创建应用或 bot。

`schema.json` 是 2.0.0 结构；[versions/1.2.0/schema.json](versions/1.2.0/schema.json) 保留原版结构。升级 Skill 不会更新已复制的 Base，也不会替换旧绑定。旧副本继续按原契约读取，需要新流程时按 [迁移说明](迁移到2.0.md) 单独处理。

## 关联和历史

配对关系用原生双向关联，只写一端并核对两端；其他关联保留原方向。自动编号供人阅读，真实 record ID 用于关联，记录键用于防止重复创建。

需求或计划实质修改前保留原范围、验收标准与确认记录。开发完成不等于需求验收；测试通过不等于已经部署。验收失败保留原记录，修好后另记一次测试结果。暂停、撤回、取消需要真实决定；无回复不能当同意。

长说明和多张截图按需放已有项目文档；机器日志、源码和安装包留在 Git、CI 或内部运行记录中，不塞进给反馈人看的字段。
