# 从单选状态迁移到流程字段

这份说明用于一次已获授权的迁移。先发布源码、annotated tag 和完整 Release，再从同一固定提交执行迁移；发布前只在独立演练副本验证。不要直接改线上字段后补发版本。

母版和已复制的项目 Base 是不同对象，分别记录链接、版本和结果。修改母版不会更新旧副本。旧契约保存在 [versions/1.2.0/schema.json](versions/1.2.0/schema.json)，不得用新契约覆盖旧绑定来消除差异。

## 迁移前保留什么

暂停目标 Linux 的后续轮次，等正在执行的工作真正结束；保留其任务、观察进度和确认依据。参考 [定时运行：绑定迁移](../skill/lark-dev-workflow/references/unattended.md)，使用正式入口，不直接覆盖配置或删除 checkpoint。

另存本次目标的字段、选项 ID、记录 ID 与当前状态、关联关系、视图筛选、实际确认来源和已确认的范围/计划版本。备份含业务数据，只保存在私有维护目录，不进入公开仓库或安装包。核对拥有编辑权限的本人账号，不更换身份绕过拒绝。

将事项分成：已结束、已确认且在执行、等待确认、暂停或受阻。状态名只是线索，不能把旧「待修复」「待处理」当作新的人工确认，也不能让历史记录重新进入执行队列。

## 要改变哪些字段

仅 01 需求、02 Bug、03 研发项的正式状态改为流程字段；其余表保持单选。按 `schema.json` 新增计划、确认人员和修订字段。确认人员从已有项目约定与真实来源核实，空母版不预填任何人的账号。

| 对象 | 流程主线 | 正常结束 | 撤销结束 |
|---|---|---|---|
| 需求、Bug | 待确认 → 可研发 → 研发中 → 待验收 | 已验收 | 已撤回 |
| 研发项 | 待确认计划 → 可开始 → 进行中 | 已交付 | 已取消 |

正常结束和撤销结束必须分别是原生 `EndDone`、`EndCancel`，不能只是同名的进行中节点。流程节点按 `stage_contract` 设置指定人员和必填字段；配置中的真实字段 ID 由目标副本解析，不复制其他 Base 的 ID。

「处理情况」单独记录正常、等待前置、受阻、暂停。暂停时保留流程位置；等待前置只适用于确实有未完成依赖。修订与确认依据放追溯视图，日常总览突出当前阶段、计划和需要谁操作。

## 存量状态如何处理

| 原状态或情况 | 迁移要求 |
|---|---|
| 待确认、尚未确认的待处理/待修复 | 保持待确认；不能补造人的确认 |
| 已确认的可研发、正在研发/修复 | 核对已有明确确认与范围，保留进度；缺计划的工作先补计划，不以迁移授权替代业务批准 |
| 待复测、待验收 | 核对候选版本、自测及实际可验收环境；满足后对应待验收 |
| 已验收、已关闭 | 保留既有验收/独立复测依据，映射真正的完成状态；不能重开已结束事项 |
| 已交付、已完成的研发项 | 保留历史交付依据，映射真正已交付；不因此替上游验收 |
| 已撤回、无需修复、已取消 | 保留原来决定及原因，映射撤销结束；重复事项仍保留主项关联 |
| 暂停、阻塞、等待前置、已转交 | 分别核实原流程位置、停止条件、依赖和当前负责人；信息不足时保留旧值，先说明具体缺口 |

**直接转换不等于迁移完成。** 飞书会把原单选选项转为普通节点，把记录当前值视为进行中的节点。旧「已完成」因此可能变成未结束；不能只按显示文字通过检查，也不能连续代点人工节点来制造新的批准记录。

上线前必须在无业务的演练副本证明：旧活动状态、已完成、已撤销分别能保留正确含义，删掉冗余节点不会清空或误转记录。若平台 UI 无法可靠保留某类记录，本次停止迁移这些存量记录，保留旧字段和绑定；不得伪报全量成功。只有空母版不受存量记录转换影响。

### 已验证的原生节点删除行为

在独立演练副本观察到：流程配置的 `convertMode=NextStage` 时，删除一个有记录停留的普通节点并保存，记录会前进到下一个节点；删除最后一个普通节点时，记录进入真正的 `EndDone`。已有 `EndDone` 记录保持不变。这是平台的删除行为，不是业务批准。原生「终止流程」会把记录设为真正的 `EndCancel`。

据此迁移有证据的旧结束记录时：先保存原始状态和实际结束依据；先对旧撤销/取消记录使用原生终止流程并回读 `EndCancel`；再将只承载已核实完成记录的旧完成节点放在普通节点末尾，核对节点顺序和受影响的记录清单，再删除该末节点并回读 `EndDone`。不能删除仍承载未完成、受阻、暂停或待确认记录的节点来推进它们。只看显示名称不算验证，必须核对终态种类与真实记录 ID。

已有已验收记录的迁移回填保留原验收来源，不能记录成迁移人员刚刚替人验收。不同旧完成状态分组处理；每组回读后再继续，不能一次删去多组节点后凭最终数量推断正确。节点重排和删除会影响整张表，必须覆盖该表中所有项目的受影响记录，不能只看当前项目。

这个行为只在已观察的原生网页方式、`NextStage` 配置下成立。目标副本的结构或保存结果不同就停止，保留现场；不调用猜测写接口、不把只读 API 成功当作写入成功。

如确需保留旧状态列作历史，它只保存迁移前快照并明确标记历史；新版流程是唯一当前进度来源。迁移后不得继续两列双写。新流程在所有目标记录完成映射和核对前不接入调度。

## 验证和恢复

在迁移后的实际副本验证以下内容，离线测试不代替这一步：

- 必填内容为空时不能完成节点；指定人员字段映射正确。
- 人手动确认后 Linux 能读到新阶段；AI 不把自己产生的变化、评论或迁移操作当作人的新确认。
- 正常推进、退回、正常结束和撤销结束读取一致；退回后旧的后续确认不自动继续有效。
- 项目隔离、评论、关联、旧失败记录与既有完成状态没有丢失；不重新创建已有事项。
- 视图筛选使用真实新节点，能看见待确认、待验收和暂停受阻事项。
- 新版运行器在完整读取、写入回读及一次授权试跑通过后，才恢复原 Linux 调度。

运行器更换绑定后仍保持暂停，恢复要沿用原有业务停止条件。迁移失败时保留现场和已完成部分，停止后续写入；按备份恢复受影响字段和绑定前先核对迁移后是否已有人的新操作，不能覆盖新反馈或在途工作。

最终分别报告：Release 固定提交、母版版本、各项目副本迁移结果、Linux 安装与扫描结果、尚未迁移的对象。不要把「已发布安装包」写成「所有线上表格已升级」。
