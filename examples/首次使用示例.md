# 首次使用示例

这些是调用 Skill 的请求示例。请附上自己的 Base 链接；示例不包含真实项目绑定或业务验收结论。

## 在共享 Base 中创建第一个项目

> 使用 $lark-dev-workflow 接入我刚复制的飞书研发工作区，创建“新产品研发”项目。这个 Base 会管理多个项目。请初始化 06 项目记录、两份项目文档章节和反馈项目选项，核实真实 ID 与章节链接，将本项目配置保存到当前工作区。正式记录由当前 Codex 按我的指令维护，范围由我确认，验收按实际执行者关系判断。保留其他项目和模板母版。

Agent 先取得平台生成的真实项目 ID 与编号，再创建项目章节并回填 URL；不会手造项目编号。项目初始化已包含在此请求中，无需再问一遍是否可以执行这些必要步骤。

## 绑定已有项目或增加另一个项目

> 使用 $lark-dev-workflow，只读接入这个 Base 中 06 项目表的 PRJ-0002“客户门户”。请核实实际项目记录后保存绑定，检查本项目的文档章节和关联范围；不要修改远端数据。

> 使用 $lark-dev-workflow，在同一个 Base 新建“内部工具”项目，沿用已有维护约定并完成必要初始化。它与已有项目分别保存配置；不要为接入另建 Base，也不要改其他项目的记录或视图。

`PRJ-0002` 只是输入示例，实际使用应给出自己项目的真实编号或记录链接。其他项目视图可共存，Skill 以查询中的 project ID 和关联核对界定范围。07 版本按项目需要使用，没有版本计划时可空。

## 验证反馈入口

只读报告中的 `ready` 只表示结构绑定通过，`write_access_verified=false` 表示未验证实际写入。母版反馈表单保持停用；副本先读取其实际共享状态。

> 使用 $lark-dev-workflow，在我提供的独立演练副本中验证反馈入口。授权当前 Codex 将本副本表单设为邀请访问、要求登录、禁止匿名后启用。选择刚初始化项目的真实“编号 · 名称”选项，提交一条“接入演练”反馈，再回读实际记录；受理时核对编号并写入该项目真实关联。分别报告共享设置、提交、回读和归属结果，不改母版或现有业务台账。

表单的“反馈项目”是原始输入，受理后的“所属项目”才是真实关联，两者不用日常重复编辑。“待确认项目”或不明确输入应留待分流，不默认归入当前聊天的项目。提交成功也不表示完整业务流程通过。

## 日常请求

> 使用 $lark-dev-workflow，查看 PRJ-0002 哪些事项需要我做决定；按真实项目 ID 核对关联和证据，只读报告。

> 使用 $lark-dev-workflow，受理这条反馈。先按反馈项目编号核实归属，保留原文、判断分类并查重；内容简短时直接使用表格和原始证据。

> 使用 $lark-dev-workflow，把这项需求更新为新修订。保留原修订的范围、AC 和确认依据，说明哪些在途工作仍适用原版；不要只保留旧版本号。

> 使用 $lark-dev-workflow，按真实测试回报更新 04，保留此前失败记录。这次只是源码测试，没有环境交付，关联交付留空；说明哪些业务项仍不能关闭。

> 使用 $lark-dev-workflow，把这条重复 Bug 归并到已核实的唯一主 Bug，记录重复依据并检查归并链无循环；不改变主 Bug 的实际阶段。


## 使用人工确认流程

> 使用 $lark-dev-workflow 处理这条反馈。先在原反馈下问清楚，再拆成需求或 Bug，并请反馈人手动推进到“可研发”。每个研发项把计划写在字段里，等我手动推进到“可开始”再做。你自测通过、所有必要工作完成且验收环境可用后，再请反馈人验收。所有标题、字段和评论都用简单直接的话。

已配置流程字段时，人的操作是完成对应节点；使用原单选字段时，改为相应状态。评论里的“同意”不替代手动状态确认。已有有效历史确认可以复用，缺少字段时先说明受影响的步骤，不自动改表。

完整正常路径、失败返工和人／AI 分工见 [Mermaid 流程图](../skill/lark-dev-workflow/references/workflow.md)。
